A good placeholder `idea.md` should be **self-documenting**: readable as a template, but also explanatory enough that someone understands what belongs in each section and what does not.

```markdown
# Project Idea

> This document captures the original concept, motivation, possibilities, and unresolved thinking behind the project.
>
> It is intentionally exploratory.
>
> Use this document to describe **why the project should exist, what problem or opportunity inspired it, and what it might become**.
>
> Do not treat ideas written here as final requirements or architectural commitments. Once an idea becomes a deliberate project decision, it should be reflected in the appropriate authoritative document such as `project.md`, `requirements.md`, or `architecture.md`.

---

## 1. Origin

### Purpose

Describe what caused the project idea to emerge.

This section should answer questions such as:

* What experience, observation, frustration, opportunity, or curiosity led to the idea?
* Was there an existing problem that repeatedly appeared?
* Was there something you wished already existed?
* Did another project expose the need for this one?
* Why are you considering this project now?

### Example

> While working on several software projects, we repeatedly encountered difficulty keeping architectural decisions, requirements, implementation plans, and project knowledge synchronized. Existing tools solved pieces of the problem but did not provide a coherent model of the project as a whole.
>
> This led to the idea of creating a system that could represent project knowledge, engineering decisions, and implementation state in a unified and machine-readable way.

## 7. Guiding Principles

### Purpose

Capture qualities that should influence future decisions.

Principles help guide the project when multiple technically valid approaches exist.

They should express preferences or values rather than implementation details.

### Example

Possible principles include:

* **Human-understandable** — important project state should remain understandable without specialized infrastructure.
* **Machine-readable** — important concepts should be representable in structured form.
* **Deterministic where possible** — identical inputs should produce predictable results.
* **Explicit over implicit** — important assumptions should be represented rather than hidden.
* **Local-first** — essential project functionality should not require remote infrastructure.
* **Composable** — capabilities should integrate without forcing unnecessary coupling.
* **Extensible** — the system should support future domains without redesigning the foundation.
* **Interoperable** — existing engineering tools should be integrated rather than unnecessarily replaced.
* **Auditable** — important decisions and changes should be traceable.
* **Progressive complexity** — simple use cases should remain simple while advanced capabilities remain possible.
```

## Document Lifecycle

This document should evolve as the idea develops.

New possibilities, observations, questions, and hypotheses may be added freely.

However, this document should **not become the authoritative specification of the project**.

As ideas mature:

```text
idea.md
   ├── validated project decisions ────────> project.md
   ├── required system behavior ──────────> requirements/
   ├── architectural decisions ───────────> architecture.md / ADRs
   ├── engineering organization ──────────> workspace.md
   └── unresolved possibilities ──────────> remain here
```

The purpose of `idea.md` is to preserve and develop the project's **conceptual origin and possibility space** without confusing exploration with commitment.

Use this rather than a mostly empty template as it shows the author the distinction between **exploration, assumptions, hypotheses, commitments, and requirements** while they fill it out.

After saving it, commit it separately:

```bash
git add docs/idea.md
git commit -m "docs: add self-documenting project idea template"
```

The next useful move is to do the same thing to `project.md`: turn it from the small placeholder we created earlier into a self-documenting template that makes very clear what constitutes **committed project truth** versus material that still belongs in `idea.md`.
