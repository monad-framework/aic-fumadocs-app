> This document defines the **current authoritative understanding of the project**.
>
> Unlike `idea.md`, which preserves exploration, possibilities, hypotheses, and unresolved thinking, this document records what the project has deliberately decided to pursue.

# Document Authority

This document represents the **project-definition layer**.

Its authority is narrower than a complete specification but stronger than exploratory material.

The conceptual flow should normally be:

```text
idea.md
   │
   │ exploration
   ▼
project.md
   │
   │ accepted project definition
   ▼
requirements/
   │
   │ required behavior and qualities
   ▼
architecture.md
   │
   │ system structure and technical strategy
   ▼
workspace.md
   │
   │ engineering/repository organization
   ▼
planning/
   │
   │ increments, milestones, work packages, tasks
   ▼
implementation
```

These relationships are not strictly one-way.

Implementation discoveries may reveal problems that require revisiting architecture, requirements, project assumptions, or even the original idea.

The important rule is that each layer answers a different category of question.

---

# Relationship to `idea.md`

`idea.md` asks:

> **What might this project be, and why is the idea worth exploring?**

`project.md` asks:

> **What have we currently decided this project actually is?**

Therefore:

```text
idea.md                              project.md
────────────────────────────────     ────────────────────────────────
possibilities                        commitments
hypotheses                           accepted project thesis
possible users                       intended users
desired capabilities                 core capabilities
possible directions                  current scope
speculative non-goals                explicit exclusions
unvalidated assumptions              planning assumptions
questions                            project-level open questions
vision                               target outcome
```

Material should not automatically move from `idea.md` into `project.md`.

It should move when the project deliberately decides:

> **We are now willing to plan and engineer against this statement.**

---

# What Does Not Belong Here

Avoid turning `project.md` into a universal project document.

Unless the information materially defines the project itself, the following should live elsewhere:

```text
Detailed functional behavior        → requirements/
Quality attributes                  → requirements/
API contracts                       → specifications/
Domain entities and invariants      → domain-model/
System components                   → architecture.md
Technology selection                → architecture.md / ADRs
Repository topology                 → workspace.md
Toolchain configuration             → workspace.md
Individual design decisions         → ADRs
Milestones                          → planning/
Epics and features                  → planning/
Work packages                       → planning/
Tasks                               → planning/
Implementation notes                → code / engineering notes
Operational procedures              → operations/
```

---

# Change Discipline

Because this document defines the project rather than merely discussing it, changes should become increasingly deliberate as the project matures.

During early discovery, frequent edits are expected.

Later, meaningful changes to sections such as:

* purpose;
* problem;
* target outcome;
* scope;
* exclusions;
* principles;
* invariants;
* success criteria;

should be treated as **project-definition changes**, not ordinary documentation edits.

The repository history should make those changes visible.

---

# Completion Criteria

This template is considered sufficiently populated to proceed into formal requirements work when:

* the project's purpose is understandable;
* the problem is clearly stated;
* intended users are identified;
* the target outcome is defined;
* meaningful scope boundaries exist;
* core capabilities are identifiable;
* important constraints are recorded;
* success criteria exist;
* major project-level unknowns are visible;
* the initial delivery boundary is at least provisionally understood.

It does **not** need to contain all possible answers before work can continue.

The goal is sufficient clarity to make the next class of decisions responsibly.

# Template Instruction

When adapting this file for a real project:

1. replace instructional placeholders with project-specific content;
2. retain explanatory text only where it remains useful to future contributors;
3. remove examples once the real content makes them unnecessary;
4. preserve unresolved questions instead of inventing answers;
5. keep exploratory material in `idea.md`;
6. move detailed requirements, architecture, workspace, and planning information into their respective layers;
7. update the `Decision Status` section as the project definition matures.

The finished `project.md` should eventually read as an **authoritative project definition**, not as a questionnaire.

Save that as `docs/project.md`, replacing the small placeholder version, then commit it:

```bash
git add docs/project.md
git commit -m "docs: establish self-documenting project definition"
```
