# AI-Native Engineering Operating System — System Architecture Baseline Review

# 1. Purpose

This review challenges the first AIEOS logical architecture before it is accepted as an architecture baseline.

The reviewed architecture is:

```text
Requirements Baseline:
RB-001

Architecture:
AIEOS-ARCH-001 v0.1.0
```

The review determines whether `AIEOS-ARCH-001`:

* satisfies `RB-001`,
* preserves `AIEOS-DOM-001`,
* assigns authoritative state unambiguously,
* maintains governance boundaries,
* handles failure correctly,
* supports local-first operation,
* provides a feasible MVP architecture,
* preserves human/agent authority separation,
* avoids premature implementation decisions,
* can safely evolve toward shared and distributed operation.

The review also determines whether:

```text
Architecture Baseline:
AB-001
```

may be accepted.

# 4. Architecture Baseline Decision

## Decision

**CHANGES REQUIRED**

`AIEOS-ARCH-001 v0.1.0` is architecturally sound in its overall direction but is **not yet ready to become Architecture Baseline AB-001**.

No finding requires replacement of the core architectural style.

The following major decisions survive review:

```text
governed control-plane architecture

ports-and-adapters integration

bounded agents

deterministic governance

modular monolith first

isolated execution workers

transactional core governance state

append-oriented consequential history

eventual consistency across external systems

reconciliation rather than distributed transactions

local-first operation

provider-neutral agent boundary
```

However, several boundaries must be made more explicit before implementation is permitted to treat the architecture as stable.

The required progression is:

```text
AIEOS-ARCH-001 v0.1.0
        ↓
AIEOS-REV-003
        ↓
architecture corrections
        ↓
AIEOS-ARCH-001 v0.2.0
        ↓
Architecture Baseline Verification
        ↓
AB-001
```

# 6. FIND-ARCH-001 — Logical Centralization Terminology

## Finding

`ARCH-P-001` currently states:

> Control is centralized logically, not necessarily physically.

The intended meaning is reasonable: governance must have coherent authority.

However, **centralized** carries stronger architectural implications than necessary and creates tension with:

```text
local-first operation

future team deployment

future distributed organizational deployment

authority partitioning
```

AIEOS does not fundamentally require one global logical center.

It requires unambiguous authority.

## Disposition

**ACCEPT-WITH-MODIFICATION — BLOCKING**

## Required replacement

### ARCH-P-001 — Governance authority is explicit and coherent

For every authoritative class of AIEOS state, the architecture SHALL define an unambiguous logical owner or explicitly governed authority partition.

Authority MAY be physically distributed.

The architecture SHALL NOT depend upon conflicting implicit writers for the same authoritative scope.

# 7. FIND-ARCH-002 — Evidence Independence, Not Externality

## Finding

`ARCH-P-007` currently states:

> Evidence is externally observable.

This is too narrow.

Valid Evidence may be produced by:

```text
local deterministic test execution

static analysis

manual inspection

local build process

sandbox execution

external CI system

runtime observation
```

The important semantic property is not that Evidence comes from an external system.

It is that required Evidence exists independently of the unsupported assertion being evaluated.

## Disposition

**ACCEPT — BLOCKING**

## Required replacement

### ARCH-P-007 — Evidence is independently inspectable

Verification architecture SHALL preserve required Evidence independently from the unsupported assertion of the Actor or Agent whose claim is being evaluated.

Evidence MAY originate from internal or external systems.

# 9. FIND-ARCH-004 — Kernel and Service Ownership Overlap

## Finding

The architecture defines an **AIEOS Kernel** that coordinates:

```text
commands
transactions
policy evaluation
state transitions
event creation
provenance
authorization checks
```

while simultaneously defining logical services that own those concerns.

Without clarification, the Kernel could become:

```text
a second Workflow owner

a second Policy owner

a second Authorization owner

a second Provenance owner
```

creating architectural ambiguity.

## Disposition

**ACCEPT — BLOCKING**

## Decision

The Kernel SHALL be treated as the **application-level governance and transaction boundary**, not as an independent domain-state owner.

The logical modules remain authoritative for their own state.

Conceptually:

```text
Command
   ↓
AIEOS Kernel
   ↓ coordinates
Domain Modules
   ↓
Authoritative Persistence
```

The Kernel:

```text
orchestrates

orders checks

establishes transaction boundary

enforces cross-module invariants

coordinates event/provenance recording
```

but SHALL NOT maintain competing copies of domain state.

---

# 10. Revised Kernel Model

The recommended model becomes:

```text
┌────────────────────────────────────┐
│           AIEOS Kernel             │
│                                    │
│ Command coordination               │
│ Transaction coordination           │
│ Cross-domain invariant enforcement │
│ Governance sequencing              │
└────────────────┬───────────────────┘
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
   Identity   Workflow   Governance
       │         │         │
       └─────────┼─────────┘
                 ▼
         Authoritative State
```

The Kernel owns coordination semantics.

Domain modules own domain state.

# 11. FIND-ARCH-005 — Actor Authentication and Principal Resolution Are Missing

## Finding

`RB-001` requires authenticated human Decisions.

The architecture identifies a:

```text
Human authentication boundary
```

but does not assign responsibility for:

```text
authentication

external identity binding

principal resolution

session identity

machine/service identity

mapping authenticated principal → AIEOS Actor
```

The Identity Service currently focuses on semantic Subject identity, which is broader than authentication.

Authentication cannot remain an unnamed boundary because every consequential:

```text
Decision

Operational Authorization

Capability Grant

Execution

Review
```

depends on trustworthy Actor identity.

## Disposition

**ACCEPT — BLOCKING**

## Required architectural responsibility

Add a logical:

> **Principal & Authentication Boundary**

or equivalent responsibility.

It SHALL:

```text
authenticate or accept trusted authentication

resolve external principal identity

bind principal → AIEOS Actor

preserve authentication context

support human principals

support automation principals

support agent execution principals
```

AIEOS MAY delegate actual credential verification to an external identity provider.

The architecture need not implement its own authentication protocol.

---

# 12. Authentication versus Semantic Identity

The architecture SHALL preserve:

```text
Authentication Identity
        ≠
AIEOS Subject Identity
```

but permit binding between them.

Example:

```text
OIDC principal:
alice@example.org
        ↓ bound-to
AIEOS Actor:
actor:019...
```

The external identity provider may be authoritative for authentication.

AIEOS remains authoritative for the internal Actor binding.

# 13. FIND-ARCH-006 — Capability and Authorization Sequencing

## Finding

Section 27 states that a Capability request is evaluated against Operational Authorization.

This is directionally correct.

However, the architecture does not make the dependency sufficiently explicit.

There are three separate concepts:

```text
Capability Definition

Operational Authorization

Capability Grant
```

The safe dependency is:

```text
Capability Definition
        +
Operational Authorization
        +
Policy
        +
Context
        ↓
Capability Grant
```

not:

```text
Capability Grant
        ↓
somehow implies Authorization
```

## Disposition

**ACCEPT — BLOCKING**

## Required architecture rule

For protected operations:

```text
Operational Authorization
        ↓
permits
Capability Grant
        ↓
enables
Execution
```

Operational Authorization SHALL NOT itself expose credentials.

Capability Grant SHALL NOT itself create normative permission.

---

# 14. Capability Lifecycle

The baseline architectural sequence SHOULD be:

```text
Actor requests operation
        ↓
Policy applicability evaluated
        ↓
Operational Authorization resolved
        ↓
Risk and Environment evaluated
        ↓
Capability Grant issued
        ↓
technical access materialized
        ↓
operation executed
        ↓
Capability Grant expires/revokes
```

Where a protected operation requires fresh authorization, validity SHALL be re-evaluated immediately before technical capability use.

# 15. FIND-ARCH-007 — External Dispatch Atomicity

## Finding

The architecture correctly avoids distributed transactions and introduces operation records.

However, a stricter invariant is needed:

> No consequential external mutation should be dispatchable unless the AIEOS record authorizing and identifying that operation has already committed successfully.

Otherwise:

```text
external mutation occurs

but

AIEOS crashes before recording intent
```

could create an untraceable side effect.

## Disposition

**ACCEPT — BLOCKING**

## Required invariant

### ARCH-INV-013 — Commit before external dispatch

A consequential external mutation SHALL be dispatched only from an operation record that has been committed to authoritative AIEOS state.

The committed operation SHALL identify at least:

```text
operation identity

Actor

requested action

target

Operational Authorization

relevant Policy state

Work Unit / Execution

idempotency identity where applicable
```

---

# 16. External Operation Sequence

The preferred logical sequence becomes:

```text
Request protected external action
        ↓
Validate governance
        ↓
Create External Operation record
        ↓
Record Event + Provenance
        ↓
COMMIT
        ↓
Dispatch adapter operation
        ↓
Observe native result
        ↓
Record result
        ↓
Reconcile authoritative native state
```

The dispatch MAY be initiated through an outbox or equivalent mechanism.

---

# 17. FIND-ARCH-008 — Deferred Operations Require Authorization Revalidation

## Finding

Section 81 currently states:

> authorization revalidation where necessary

for deferred external operations.

For protected remote side effects, this is too permissive.

An operation may be queued while:

```text
authorization is revoked

policy changes

risk increases

environment classification changes

actor scope changes
```

before connectivity returns.

## Disposition

**ACCEPT — BLOCKING**

## Decision

Protected deferred external operations SHALL re-evaluate time-sensitive governance at dispatch time.

The sequence SHALL be:

```text
pending operation
        ↓
connectivity restored
        ↓
re-evaluate:
    Policy
    Operational Authorization
    Capability eligibility
    Environment
    Risk
        ↓
dispatch if still permitted
```

The original authorization remains part of history.

It does not automatically remain valid for future dispatch.

# 18. FIND-ARCH-009 — Local-First and Multi-Node Authority Topology

## Finding

The architecture correctly supports:

```text
single local instance
        ↓
team instance
        ↓
organizational deployment
```

but does not yet specify the minimum authority rule needed to prevent future accidental multi-master behavior.

If two AIEOS instances both believe they are authoritative for:

```text
same Workflow Instance

same Decision

same Authorization

same Assertion scope
```

the system could violate its own single-authority semantics.

## Disposition

**ACCEPT — BLOCKING**

## Required architectural principle

### ARCH-P-013 — No implicit multi-writer authority

AIEOS SHALL NOT assume unrestricted multi-writer authority for the same authoritative scope.

Shared or distributed deployments SHALL use one or more explicit mechanisms such as:

```text
single authoritative owner

workspace authority partition

subject namespace ownership

lease/leadership

explicit replication authority

governed merge/reconciliation
```

The exact synchronization mechanism is deferred.

The authority topology is not.

---

# 19. Local-First Authority Model

The architecture SHALL distinguish:

```text
local availability

from

authoritative ownership
```

A local instance may retain a complete usable projection without being authorized to originate every class of authoritative mutation.

Conceptually:

```text
Local copy
    ≠
Local authority
```

unless configured authority explicitly grants both.

---

# 20. Distributed Conflict Rule

If two instances produce conflicting authoritative mutations because of partition or misconfiguration:

```text
conflict SHALL be represented
```

rather than silently choosing:

```text
last writer wins
```

unless an explicit Policy defines that resolution as legitimate for that state class.

---

# 21. FIND-ARCH-010 — External Authoritative Fact Freshness

## Finding

AIEOS permits external systems to remain authoritative for native facts.

This is correct.

However, protected governance may require facts such as:

```text
CI status

current Git revision

deployment state

security scan status

production environment status
```

and the architecture does not yet specify when cached external state is sufficiently fresh to support a Decision or protected Transition.

## Disposition

**ACCEPT — BLOCKING**

## Required concept

Introduce an **Authoritative Read Contract** or equivalent semantics.

For an externally authoritative Assertion, AIEOS SHALL be able to determine:

```text
authority source

observed value

observed time

source version/revision

freshness state

validity state
```

---

# 22. Protected Decisions Using External Facts

Policy SHALL be able to require:

```text
fresh authoritative read

or

recorded observation within freshness threshold

or

specific immutable native revision
```

before a protected transition proceeds.

Example:

```text
Production deployment requires:

CI status = passed

for commit abc123

observed within permitted freshness window
```

not merely:

```text
CI passed at some point.
```

---

# 23. FIND-ARCH-011 — Configuration Ownership Is Missing

## Finding

`REQ-CONF` is mapped to:

```text
Governance / configuration subsystem
```

but the architecture defines no clear configuration owner.

Configuration may govern:

```text
Policy selection

Workflow registration

Authority Bindings

Risk defaults

integration bindings

agent profiles

Environment classification

retention

feature availability
```

Without explicit ownership, configuration can become hidden authority.

## Disposition

**ACCEPT — BLOCKING**

## Decision

Add a logical **Configuration Service** or explicit Configuration responsibility within the Governance layer.

It SHALL own AIEOS-managed configuration metadata and versioning.

Configuration that changes consequential governance SHALL be:

```text
validated

versioned

attributable

auditable

subject to applicable Decision/Authorization
```

---

# 24. Configuration Is Not Policy

The architecture SHALL preserve:

```text
Configuration
    ≠
Policy
```

Configuration may determine which Policy applies.

Policy determines governed rules.

Example:

```text
Configuration:
project X uses policy set SECURITY-2

Policy:
production changes require security review
```

# 25. FIND-ARCH-012 — MVP Approval/Authorization Conflation

## Finding

The MVP sequence currently contains:

```text
Plan approved
        ↓
Implementation capability requested
        ↓
Policy + Authorization evaluated
        ↓
Sandbox created
```

but does not show where the Operational Authorization permitting repository mutation came from.

This creates a dangerous ambiguity because the domain baseline explicitly states:

```text
Approval
    ≠
Operational Authorization
```

A human approving a Plan does not necessarily authorize an Agent to mutate a repository.

## Disposition

**ACCEPT — BLOCKING**

## Required revised MVP sequence

The relevant portion SHALL become:

```text
Plan proposed
        ↓
Plan Decision / Approval
        ↓
Execution authorization requested
        ↓
Policy evaluated
        ↓
Operational Authorization granted
        ↓
Capability Grant issued
        ↓
Sandbox created
        ↓
Implementation Agent executes
```

Operational Authorization MAY be:

```text
explicitly human-granted

or

deterministically policy-derived from prior authority
```

but the derivation MUST be explicit.

---

# 26. Merge Authorization in MVP

The later merge sequence SHALL likewise preserve:

```text
Review accepted
        ↓
Human Approval
        ↓
Merge Operational Authorization
        ↓
Merge Capability Grant
        ↓
source-control adapter executes merge
```

unless Policy explicitly permits a deterministic authorization derivation.

# 27. FIND-ARCH-013 — Projection Use in Protected Decisions

## Finding

The architecture correctly treats projections as derived.

However, it does not explicitly prohibit stale projections from becoming the basis for protected governance.

Example:

```text
dashboard says tests passed
```

may reflect stale projected state even though authoritative CI state has changed.

## Disposition

**ACCEPT — NON-BLOCKING**

## Required rule

### ARCH-INV-014 — Protected decisions do not trust projections implicitly

A derived Projection SHALL NOT satisfy a protected governance prerequisite merely because it displays the desired value.

Its source authority, freshness, and validity SHALL satisfy applicable Policy.

# 28. FIND-ARCH-014 — Atomic Consequential Mutation Envelope

## Finding

Section 37 correctly proposes atomic persistence for:

```text
Workflow transition
+
Lifecycle State
+
Transition record
+
Event
+
Provenance
```

The concept should be generalized.

Other consequential mutations also require atomic governance metadata.

Examples:

```text
Decision recorded

Operational Authorization granted

Capability Grant issued

Assertion accepted

Policy Exception accepted
```

## Disposition

**ACCEPT-WITH-MODIFICATION — NON-BLOCKING**

## Required architecture rule

For any consequential authoritative mutation, AIEOS SHOULD commit the domain mutation together with the minimum audit/provenance records required to explain that mutation.

Conceptually:

```text
Authoritative State Mutation
        +
Domain Record
        +
Required Event
        +
Required Provenance
        =
Atomic Consequential Mutation Envelope
```

The exact physical persistence representation is deferred.

# 29. FIND-ARCH-015 — Environment Ownership Is Ambiguous

## Finding

Environment concerns currently appear across:

```text
Identity Service

Execution Manager

Governance Service
```

This is semantically reasonable but state ownership is not explicit.

## Disposition

**ACCEPT — NON-BLOCKING**

## Decision

Separate Environment concerns:

```text
Environment semantic identity
    → Identity Service

AIEOS Environment metadata/classification
    → Configuration / Knowledge responsibility

native runtime state
    → external Environment provider

execution binding to Environment
    → Execution Manager

Environment-specific governance
    → Governance Service
```

No single module needs to own every aspect of Environment.

Each authoritative fact must nevertheless have exactly one owner.

# 30. FIND-ARCH-016 — Incident Ownership

## Finding

Requirement mapping currently assigns `REQ-INC` to:

```text
Work Coordination + Observation
```

but Incident is itself an Artifact with lifecycle and relationships.

Creating a dedicated Incident Service now would likely be premature.

Leaving ownership completely implicit is also undesirable.

## Disposition

**ACCEPT-WITH-MODIFICATION — NON-BLOCKING**

## Decision

For the initial architecture:

```text

    → Knowledge Service

Incident Work Unit coordination
    → Work Coordination Service

Incident-triggering Observations
    → Observation Gateway

Incident workflow state
    → Workflow Service
```

A future dedicated Incident subsystem MAY be extracted if operational evidence justifies it.

# 31. FIND-ARCH-017 — Modular Monolith First

## Finding

The architecture recommends:

```text
modular monolith
+
isolated workers
```

for the MVP.

## Disposition

**NO-CHANGE — NON-BLOCKING**

This is appropriate.

The domain contains many strongly related transactional invariants.

Beginning with microservices would introduce unnecessary:

```text
distributed transactions

cross-service authorization

event-ordering problems

schema coordination

deployment complexity

failure surfaces
```

before the domain is empirically stable.

The logical module boundaries are sufficient to preserve future extraction options.

## Disposition

**NO-CHANGE — NON-BLOCKING**

# 33. FIND-ARCH-019 — Event Ledger Without Mandatory Event Sourcing

## Finding

The architecture requires append-oriented consequential history but does not mandate full event sourcing.

## Disposition

**NO-CHANGE — NON-BLOCKING**

This is the correct balance.

AIEOS needs:

```text
historical events

auditability

provenance

correction history
```

but does not yet have evidence that every current state should be reconstructed solely through event replay.

# 34. FIND-ARCH-020 — Reconciliation Instead of Distributed Transactions

## Finding

The architecture rejects mandatory distributed two-phase commit across engineering providers.

## Disposition

**NO-CHANGE — NON-BLOCKING**

This is strongly supported.

External engineering systems cannot generally participate safely in one global atomic transaction.

The architecture should retain:

```text
local transactional governance
+
explicit operation state
+
idempotency
+
reconciliation
+
compensation
```

instead.

# 67. Most Important Finding

The most consequential issue discovered by this review is not a technology problem.

It is the need to make the following chain explicit everywhere:

```text
Actor identity
    ↓
Decision authority
    ↓
Operational Authorization
    ↓
Capability Grant
    ↓
Execution
```

Without that separation, AIEOS would risk becoming an agent automation framework with governance metadata layered on top.

With that separation, governance becomes structurally enforceable.

This distinction is central to the product.

---

# 68. Second Most Important Finding

The second major architectural requirement is:

```text
local-first
    ≠
implicit multi-master
```

A local-first system may:

```text
operate locally

retain local knowledge

execute local tasks

continue offline
```

without every local instance becoming simultaneously authoritative for every shared state class.

Authority topology must remain explicit.

---

# 69. Third Most Important Finding

External engineering reality cannot be modeled as a simple API call.

For consequential side effects, the real architecture is:

```text
governed intent
    ↓
committed operation
    ↓
dispatch
    ↓
uncertain external world
    ↓
observation
    ↓
reconciliation
```

This means **reconciliation is not merely synchronization infrastructure**.

It is part of the core correctness model of AIEOS.

---

# 70. Architecture Thesis After Review

The reviewed architecture can be stated more precisely as:

> **AIEOS is a locally operable, governance-centered engineering control plane whose authoritative state is partitioned explicitly, whose agents act only through bounded and authorized capabilities, whose consequential external effects originate from committed governed operations, and whose understanding of external reality is maintained through evidence, observation, and reconciliation.**

That formulation better captures the system architecture than:

> "an AI application that automates the SDLC."
