# Architecture Decision Record Catalog

The Architecture Decision Record Catalog is the authoritative backlog of consequential architectural decisions that remain unresolved in Monad.

The Requirements corpus establishes **what Monad must accomplish and what properties it must preserve**.

The ADR corpus establishes **which architectural choices Monad makes in order to satisfy those requirements**.

The Specifications corpus will then establish **the precise contracts, structures, behaviors, invariants, and interfaces that implement those decisions**.

This separation is intentional:

> Requirements establish obligations. ADRs resolve consequential choices. Specifications define exact contracts.

An unresolved question should not remain indefinitely embedded at the bottom of a requirements document. Once the question is understood well enough to affect architecture, it belongs here.

---

## Purpose

This catalog exists to:

* make unresolved architectural choices visible,
* prevent important decisions from being made implicitly during implementation,
* consolidate overlapping questions from multiple requirement families,
* establish dependency order among decisions,
* distinguish architecture decisions from specification questions,
* preserve rejected alternatives and decision rationale,
* identify assumptions requiring experimentation,
* connect requirements to architecture,
* and provide the decision foundation from which specifications can be derived.

The ADR backlog is not a list of everything Monad does not yet know.

Only questions whose answers materially constrain the architecture belong here.

---

## Decision Boundary

A question belongs in an ADR when different reasonable answers would materially change one or more of:

* system boundaries,
* semantic architecture,
* persistence architecture,
* authority or governance behavior,
* execution semantics,
* integration strategy,
* consistency guarantees,
* lifecycle behavior,
* portability,
* extensibility,
* security boundaries,
* local-first behavior,
* AI autonomy boundaries,
* or major implementation constraints.

A question generally belongs in a Specification instead when it asks:

* what fields an entity contains,
* the exact shape of a record,
* the exact API payload,
* allowed enum values,
* validation rules,
* exact state-transition tables after the architectural model is chosen,
* exact error codes,
* serialization details,
* schema syntax,
* command syntax,
* or other implementable details inside an already-selected architecture.

For example:

> Should semantic relationships be modeled as a graph?

may be architectural.

> Should the graph be persisted using a graph database?

is architectural.

> What fields exist on a `Relationship` record?

is specification-level.

---

# ADR Lifecycle

Each ADR SHALL move through a deliberate lifecycle.

```text
Backlog
   ↓
Proposed
   ↓
Under Review
   ↓
Accepted
   ↓
Implemented
```

Alternative terminal or transitional states may include:

```text
Rejected
Superseded
Deferred
Experimental
Withdrawn
```

An ADR marked **Accepted** represents the current architectural decision unless another accepted ADR explicitly supersedes it.

Acceptance does not imply implementation.

Implementation does not make an undocumented architectural choice acceptable retroactively.

# Decision Priority

The backlog is divided into dependency waves.

```text
Wave 1 — Semantic Foundation
        ↓
Wave 2 — State, Time, and Persistence
        ↓
Wave 3 — Authority and Governance
        ↓
Wave 4 — Execution
        ↓
Wave 5 — Integration and Reconciliation
        ↓
Wave 6 — Locality and Reproducibility
        ↓
Wave 7 — AI Interaction
        ↓
Wave 8 — Verification and Assurance
```

Later ADRs may be explored before earlier ones are accepted, but they SHOULD NOT be finalized when their answer depends on an unresolved upstream architectural decision.

# Wave 1 — Semantic Foundation

## ADR-001 — Semantic Identifier Strategy

**Status:** Backlog
**Priority:** Critical
**Primary requirements:** `REQ-ID`, `REQ-SEM`

Determine the fundamental identifier strategy for semantic Subjects.

Questions include:

* What concrete identifier format should Monad use?
* Should identifiers be opaque or meaning-bearing?
* Should identifiers be UUID-like, URI-like, content-derived, hierarchical, or another form?
* Which properties, if any, may safely be encoded into identifiers?
* How should identifiers survive rename, relocation, representation replacement, and native-system migration?

### Decision must establish

* identifier invariants,
* generation strategy,
* collision behavior,
* durability expectations,
* serialization expectations,
* and what identifiers deliberately do **not** mean.

## ADR-010 — Graph-Shaped Semantics vs Graph Database

**Status:** Backlog
**Priority:** Critical
**Primary requirements:** `REQ-SEM`

Determine whether Monad's graph-shaped semantic model requires graph-native persistence.

The default assumption SHALL NOT be:

> graph-shaped domain = graph database.

The decision must compare graph-native persistence against simpler alternatives including relational and indexed representations.

A graph database should be selected only if it provides material value that cannot be achieved adequately through simpler persistence.

# Questions That Should Remain Open

Some questions need neither an ADR nor a Specification yet.

They should remain explicit research questions when:

* current evidence is insufficient,
* the decision is not yet consequential,
* no near-term implementation depends on the answer,
* or resolving the question now would create premature architecture.

The backlog should therefore resist the temptation to make every uncertainty immediately decidable.

> Making uncertainty explicit is preferable to disguising it as architecture.
