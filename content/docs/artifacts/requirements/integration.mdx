# Integration Requirements

Monad exists within an engineering ecosystem that already contains capable systems:

* Git,
* GitHub and GitLab,
* filesystems,
* editors,
* CI platforms,
* package managers,
* artifact registries,
* databases,
* cloud providers,
* deployment systems,
* issue trackers,
* observability platforms,
* documentation systems,
* security scanners,
* build systems,
* and many others.

Monad should not recreate those systems merely to gain control over them.

Its role is different.

Monad adds a semantic and governance layer that can connect engineering facts across otherwise separate systems:

```text
native systems
      ↓
integrations
      ↓
semantic identity
relationships
authority
provenance
evidence
governance
context
      ↓
Monad
```

The governing default is therefore:

> **If another system already owns a capability well, Monad should integrate with it before attempting to reimplement it.**

Integration is not a thin API wrapper.

A useful integration must preserve enough native meaning that Monad can understand what the external system knows, what it can do, what it owns, what changed, and which parts of that information Monad may safely rely upon.

# Foundational integration requirements

## REQ-INT-001 — Monad SHOULD integrate before reimplementing mature native capability

When an external system already provides a capability effectively, Monad SHOULD prefer using that capability rather than creating a competing implementation without sufficient justification.

Examples include:

```text
version control       → Git
issue tracking        → GitHub / GitLab / Jira
package publication   → npm / crates.io / OCI registries
deployment execution  → native deployment platforms
cloud provisioning    → provider-native APIs / established tools
```

---

## REQ-INT-002 — Reimplementation MUST require an explicit engineering justification when a suitable native capability already exists

Potential justification MAY include:

* native capability is unavailable locally,
* required semantics cannot be represented,
* unacceptable reliability constraints,
* unacceptable security constraints,
* portability requirements,
* reproducibility requirements,
* unacceptable lock-in,
* unavailable automation interface,
* unacceptable operational complexity,
* or demonstrated architectural incompatibility.

Convenience alone SHOULD NOT automatically justify replacement.

---

## REQ-INT-003 — Monad MUST distinguish integration from ownership

Being connected to a native system does not mean Monad owns that system's data or semantics.

---

## REQ-INT-004 — Monad MUST distinguish integration from synchronization

An integration provides access to a system.

Synchronization and reconciliation are behaviors built upon that access.

---

## REQ-INT-005 — Monad MUST distinguish integration from semantic identity

Native references identify native resources.

Monad semantic identity MAY span multiple native systems.

---

## REQ-INT-006 — Monad MUST distinguish integration capability from governance authority

An adapter being technically capable of deleting a repository does not imply that any Actor is authorized to delete it.

---

# Native systems remain first-class

## REQ-INT-007 — Native engineering systems MUST remain first-class sources of native facts

Monad SHOULD NOT fabricate native state when the source system can provide it.

---

## REQ-INT-008 — Native systems SHOULD retain ownership of the capabilities they are explicitly integrated to provide

Examples:

```text
Git:
  owns commit identity and repository history

GitHub:
  owns native issue and pull-request state

OCI registry:
  owns publication state for OCI artifacts

deployment platform:
  owns native deployment records
```

---

## REQ-INT-009 — Monad SHOULD preserve access to native tools independently of Monad where practical

Monad SHOULD avoid creating an architecture in which ordinary engineering work becomes impossible merely because the semantic control layer is unavailable.

---

## REQ-INT-010 — Direct native-system use MAY remain valid unless governance explicitly prohibits it

This allows engineers to continue using:

* Git CLI,
* native web interfaces,
* IDE integrations,
* package-manager commands,
* infrastructure tools,
* and provider consoles.

Monad must be capable of reconciling externally initiated changes.

# Integration boundaries

## REQ-INT-011 — Every integration SHOULD define its responsibility boundary

An integration SHOULD make clear:

* what it observes,
* what it can mutate,
* what native concepts it understands,
* which native concepts it intentionally ignores,
* what events it consumes,
* what guarantees it provides,
* and what it does not own.

---

## REQ-INT-012 — Integration boundaries SHOULD be narrower than the native provider's entire API where only a subset is needed

Monad SHOULD avoid importing unnecessary capability.

---

## REQ-INT-013 — Integration boundaries SHOULD reflect engineering semantics rather than provider marketing categories

---

## REQ-INT-014 — Native-provider details SHOULD remain encapsulated behind provider-specific adapters where appropriate

---

## REQ-INT-015 — Provider abstraction MUST NOT erase native semantics that materially affect correctness

# Integration architecture

A conceptual integration architecture may resemble:

```text
Monad
  │
  ├── semantic integration contract
  │
  ├── capability model
  │
  ├── policy / authority evaluation
  │
  └── reconciliation
          │
          ▼
     provider adapter
          │
          ▼
      native system
```

The semantic contract defines what Monad means.

The provider adapter defines how that meaning maps to a specific system.

## REQ-INT-017 — Integration contracts SHOULD be independent of transport where practical


# Integration anti-patterns

## Reimplement everything

This creates unnecessary complexity and weak native-tool compatibility.

---

## Wrapper equals integration

An API client with no semantic mapping, provenance, error model, or authority boundary is incomplete.

---

## Lowest-common-denominator abstraction

Useful provider capability disappears in pursuit of superficial uniformity.

---

## Provider concepts become the domain model

The first integration accidentally defines Monad's ontology.

---

## Credentials equal authority

Technical permission bypasses governance.

---

## Event equals truth

Webhook payloads become the only model of native state.

---

## Poll everything

Scalability and provider limits are ignored.

---

## Cache forever

Mutable native state becomes stale while appearing current.

---

## Ignore native IDs

Reconciliation and forensic inspection become unnecessarily difficult.

---

## Path equals identity

Moves and renames produce false semantic churn.

---

## Provider-specific fields everywhere

The core model becomes coupled to one external system.

---

## Hide provider-specific differences

Critical semantics disappear behind an abstraction.

---

## Green API response means done

Native state is not re-observed.

---

## Retry until success

Non-idempotent operations produce duplicate side effects.

---

## Import all available data

Privacy, security, and storage risk expand without engineering value.

---

## Plugin installed means trusted

Third-party code gains excessive privilege.

---

## Direct native edits are corruption

Engineers lose the ability to use their normal tools.

---

## Monad becomes a mandatory proxy

Every native operation unnecessarily depends on Monad availability.

---

# Capability example

```yaml

    read: true
```

```yaml

  issue_update: true
```

```yaml
close_release_blocker:
```

```text
adapter can close

credential can close
+
Actor can request close
+
approval missing
=
operation not authorized
```

This is the intended distinction.

# Relationship to the system model

Integrations provide representations of native reality.

They do not define the entire system model.

Conceptually:

```text
Native system
    ↓
Integration
    ↓
Native observations
    ↓
Semantic binding
    ↓
System model
```

The semantic layer may then connect:

```text
Git commit
    ↓ implements

Requirement
    ↓ verified-by

CI run
    ↓ supports

Release
```

No individual native system needs to understand the whole relationship graph.

That cross-system meaning is one of Monad's primary responsibilities.

---

# Relationship to authority

Integration enables action.

Authority legitimizes action.

Those are different.

```text
Provider capability
      ↓
Adapter capability
      ↓
Actor capability
      ↓
Authority
      ↓
Policy
      ↓
Authorized operation
```

Skipping any of these distinctions risks turning technical reach into uncontrolled power.

---

# Relationship to reconciliation

Integration supplies:

```text
what the native system says
```

Reconciliation determines:

```text
how that state relates to what Monad believes
```

Therefore:

```text
Integration
    ↓
Observation
    ↓
Reconciliation
    ↓
Possible governed remediation
```

---

# Relationship to provenance

Every integration is a provenance boundary.

A normalized Claim should be able to retain:

```text
native provider
native resource
native revision
observation time
adapter
transformation
```

Otherwise the semantic model becomes disconnected from the source that justified it.

---

# Relationship to Evidence

Native systems frequently produce Evidence:

```text
Git
  → commit state

CI
  → test results

registry
  → published digest

deployment platform
  → deployment state

observability system
  → runtime measurements
```

Integration makes that Evidence addressable.

It does not automatically establish the Claim that the Evidence is sufficient to prove.

---

```text
  ↓

  ↓

  ↓
Evaluate policy
  ↓
Authorize
  ↓

  ↓

  ↓

  ↓
Observe
  ↓

  ↓

  ↓
Reconcile
```

# Relationship to portability

Provider-neutral architecture matters because native systems change.

A repository may move.

A company may replace issue trackers.

A package may move registries.

An AI provider may change.

Monad should preserve engineering meaning through those changes wherever the underlying Subject remains the same.

---

# Relationship to local-first operation

Integration should not force the entire engineering environment into remote dependency.

A healthy architecture may support:

```text
local native systems
    +
optional remote integrations
    +
cached remote knowledge
    +
explicit freshness
```

rather than:

```text
remote provider unavailable
    =
engineering system unusable
```

# Definition of Ready

An integration is ready for implementation when:

* the native system is identified,
* the engineering capability it owns is understood,
* integration has been justified against reimplementation,
* scope is defined,
* semantic boundaries are defined,
* native identity is understood,
* supported capabilities are defined,
* authentication requirements are known,
* permission requirements are known,
* expected authority boundaries are known,
* observation semantics are defined,
* mutation semantics are defined where applicable,
* event behavior is understood,
* consistency guarantees are known,
* failure modes are identified,
* reconciliation expectations are defined,
* provider compatibility is understood,
* security constraints are known,
* and verification criteria exist.

---

# Definition of Done

An integration is complete enough when:

* native resources retain native identity,
* semantic identity remains separate,
* capability boundaries are explicit,
* credential permissions are explicit,
* authority remains separately governed,
* observations preserve source and freshness,
* mutations expose side effects,
* errors are structured,
* provider-native error details remain inspectable,
* retry behavior is safe,
* partial failure is explicit,
* concurrency is handled appropriately,
* event semantics are defined,
* reconciliation works where required,
* adapter compatibility is tested,
* sensitive data is protected,
* operational health is observable,
* native-system use remains possible where intended,
* provider-specific semantics are not silently erased,
* and the integration can be traced from Monad operation to native outcome.

---

# Governing principle

Monad should always be able to ask:

> Which system owns this native capability?

> What native resource are we actually talking about?

> What immutable identifier does that system provide?

> Which semantic Subject does the resource represent?

> Which properties belong to the provider?

> Which properties belong to Monad?

> What can this adapter technically do?

> What can the configured credentials do?

> What may this Actor legitimately do?

> Which policy governs the operation?

> What native state was actually observed?

> When was it observed?

> Which revision did it represent?

> Was the observation complete?

> Was it cached or current?

> What transformation produced the normalized state?

> Did that transformation lose information?

> What happened when Monad attempted a native operation?

> Was the provider response successful?

> Did the native state actually change?

> Can that result be verified?

> What happens if an engineer changes the native system directly?

> Can Monad reconcile the difference without destroying legitimate work?

> Could this provider be replaced without destroying semantic identity?

> Does this abstraction preserve useful provider-specific capability?

> Is the integration giving Monad new semantic value—or merely duplicating the external system?

The desired architecture is therefore not:

```text
Monad replaces engineering tools
```

but:

```text
Native engineering systems
        ↕
Explicit integration contracts
        ↕
Semantic identity + provenance
        ↕
Authority + policy
        ↕
Reconciliation + verification
        ↕
Monad
```

> **Monad should integrate with native systems deeply enough to understand and govern engineering reality, but lightly enough that those systems remain first-class, independently useful, and authoritative for the capabilities they already own.**
