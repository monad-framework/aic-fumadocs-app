# Portability Requirements

Portability in Monad is not merely:

> Can the software execute on another machine?

That matters, but it is only one layer.

Monad is intended to preserve engineering knowledge and system meaning across changes in:

* filesystem location,
* repository layout,
* operating system,
* machine,
* runtime,
* database,
* service provider,
* issue tracker,
* source-control host,
* package registry,
* AI provider,
* execution environment,
* deployment platform,
* organization,
* and time.

A portable engineering system should survive changes in its surrounding tools without losing the meaning of the system it describes.

The deeper portability question is therefore:

> **Can the engineering record remain intelligible, inspectable, reconstructable, and useful when its original environment changes or disappears?**

# Foundational portability requirements

## REQ-PORT-001 — Monad MUST preserve semantic identity independently of filesystem location

Moving:

```text
docs/requirements/auth.md
```

to:

```text
engineering/requirements/authority.md
```

MUST NOT create a new semantic Subject merely because the path changed.

---

## REQ-PORT-002 — Monad MUST preserve semantic identity independently of repository location

A repository transfer or rename SHOULD NOT redefine the identity of Subjects whose semantic continuity remains established.

---

## REQ-PORT-003 — Monad MUST distinguish semantic identity from native-provider identity

A GitHub repository ID, local filesystem path, database row ID, or external issue number MAY participate in identity binding.

None automatically defines the entire semantic identity of the governed Subject.

---

## REQ-PORT-004 — Core engineering records SHOULD remain inspectable without dependence on a single proprietary service

---

## REQ-PORT-005 — Loss of an optional external provider MUST NOT make the locally retained engineering record unintelligible

---

## REQ-PORT-006 — Portability MUST preserve meaning, not merely bytes

A successful byte-for-byte export that loses:

* relationships,
* authority semantics,
* provenance,
* lifecycle state,
* revision information,
* evidence links,
* or identity bindings

is not sufficient semantic portability.

# Portability layers

Monad SHOULD reason about portability across several distinct layers:

```text
semantic portability
        ↓
artifact portability
        ↓
data portability
        ↓
schema portability
        ↓
configuration portability
        ↓
runtime portability
        ↓
environment portability
        ↓
provider portability
```

These layers are related but not interchangeable.

# Portability anti-patterns

## Path is identity

Repository restructuring breaks the semantic model.

---

## Database primary key is identity

Changing storage becomes equivalent to changing the engineering system.

---

## Provider object is the domain object

Leaving the provider requires rewriting the ontology.

---

## SaaS is the archive

Critical project knowledge disappears when an account or provider disappears.

---

## Export is a CSV dump

Relationships and semantics are flattened beyond recovery.

---

## Proprietary serialized runtime state

Only the original application can interpret the records.

---

## Hidden global configuration

A project works only on the original developer's machine.

---

## Absolute paths everywhere

Moving the project breaks references.

---

## Silent lossy migration

Information disappears while the migration reports success.

---

## Rewrite history during migration

Old provider references and prior states vanish.

---

## New provider means new identity

Stable Subjects are unnecessarily recreated.

---

## Import duplicates everything

Existing semantic Subjects are not reconciled.

---

## Copy means same project

Template instantiations accidentally share identity.

---

## Fork means unrelated project

Lineage disappears.

---

## Portability means lowest common denominator

Useful provider-specific capability is discarded.

---

## Portable means reproducible

State movement is confused with deterministic recreation.

---

## Backup means recovery

Backups are never tested.

---

## Human readable means semantically complete

Pretty Markdown exists, but relationships and provenance disappear.

---

## Machine readable means future proof

A JSON file with undocumented semantics remains opaque.

---

## Preserve bytes, lose meaning

The archive technically survives but the engineering record does not.

# Relationship to semantic identity

Portability depends first on identity.

If identity is equivalent to location:

```text
move file
   =
new Subject
```

If identity is semantic:

```text
move file
   =
new Representation location
```

That distinction is foundational.

---

# Relationship to Representations

Representations are expected to move and evolve.

A Requirement may appear as:

```text
Markdown
GitHub issue
database record
generated website page
API representation
archive record
```

Portability means these forms can change without silently redefining the underlying Subject.

---

# Relationship to integrations

Integrations introduce provider-specific identity and behavior.

Portability requires Monad to preserve:

```text
native meaning
+
semantic independence
```

rather than choosing only one.

---

# Relationship to reconciliation

After migration, Monad may need to reconnect to native systems.

That produces:

```text
imported semantic state
        +
new native observations
        ↓
reconciliation
```

Reconciliation determines whether:

* bindings remain valid,
* provider state changed,
* imported state is stale,
* native resources moved,
* new native references should be attached.

---

# Relationship to Evidence

Evidence can outlive the tool that produced it.

Therefore a future engineer should ideally be able to determine:

```text
what produced this Evidence
which revision it concerned
when it was produced
what Claim it supported
what environment it represented
```

even if the producing CI platform or provider no longer exists.

---

# Relationship to Verification

Verification is scoped.

Migrating a project may preserve the historical Verification while invalidating its applicability to the new environment.

For example:

```text
verified on Linux
```

remains historical truth after migration.

It does not automatically become:

```text
verified on Windows
```

---

# Relationship to releases

Releases should survive movement among registries and deployment systems.

The Release Subject may remain:

```text
REL-0007
```

while its native publication references change.

---

# Relationship to traceability

Traceability provides semantic continuity.

A portable project should retain chains such as:

```text
Requirement
   ↓ specified-by

Specification
   ↓ implemented-by

Component
   ↓ verified-by

Verification
   ↓ supported-by

Evidence
   ↓ released-in

Release
```

even after moving to another machine or provider.

---

# Relationship to reproducibility

Portability allows engineering state to travel.

Reproducibility allows engineering results to be reconstructed.

A strong system should support both, but they remain separate Claims.

---

# Relationship to local-first design

Local-first is one of Monad's strongest portability mechanisms.

When essential state is locally available and represented using documented semantics, migration becomes easier because the project is not fundamentally trapped inside remote application state.

---

# Definition of Ready

A portability capability is ready for implementation when:

* the Subjects being moved are identified,
* stable identity rules are defined,
* Representation boundaries are understood,
* source and destination environments are known,
* portable data is identified,
* local-only data is identified,
* provider-specific data is identified,
* serialization requirements are defined,
* schema/version requirements are defined,
* compatibility requirements are known,
* migration behavior is specified,
* conflicts are understood,
* security constraints are known,
* privacy constraints are known,
* backup and recovery requirements are known where applicable,
* and verification criteria exist.

---

# Definition of Done

A portability capability is complete enough when:

* semantic identity survives the supported migration,
* Representation locations may change safely,
* native references remain preserved,
* relationships survive,
* lifecycle state survives,
* provenance survives,
* historical state remains historical,
* authority scope is preserved or explicitly revalidated,
* portable records identify their format version,
* migration incompatibilities fail explicitly,
* lossy transformations are reported,
* secrets are not inadvertently exported,
* external dependencies remain identifiable,
* import detects conflicts,
* round-trip tests pass,
* fresh-machine restoration has been demonstrated where required,
* and the resulting project remains intelligible without reconstructing meaning manually.

---

# Governing principle

Monad should always be able to ask:

> If this file moves, is it still the same Subject?

> If this repository moves, is it still the same project?

> If the Git host changes, which identities remain stable?

> If the database changes, does the domain model remain intact?

> If the operating system changes, which assumptions become invalid?

> If the provider disappears, what engineering knowledge remains locally inspectable?

> If the UI disappears, can engineers still understand the record?

> If the serialization format changes, can old records still be interpreted?

> If a project is copied, is it another working copy or a new project?

> If a system splits, should identity continue or branch through lineage?

> If two systems merge, what historical identities survive?

> If Evidence moves, can we still tell what produced it?

> If Verification was performed in another environment, is it still applicable?

> If authority records are imported, do they still grant authority here?

> If a provider is replaced, can semantic Subjects retain their identity?

> If a future engineer receives nothing but the archive, can they reconstruct what the project meant?

The portability objective is not:

```text
everything becomes provider-neutral
```

nor:

```text
everything becomes plain text
```

nor:

```text
every environment behaves identically
```

It is:

```text
stable semantic identity
        +
documented portable representations
        +
preserved provenance and history
        +
explicit environment/provider differences
        +
verifiable migration
        +
local inspectability
        ↓
engineering meaning survives change
```

> **Monad should be portable enough that changing where engineering knowledge lives does not silently change what that knowledge means.**
