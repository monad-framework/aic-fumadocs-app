# Reconciliation Requirements

Monad does not own every engineering fact.

Source repositories own commits and branches.

Issue trackers own their native issues.

Package registries own published packages.

Deployment platforms own their deployment state.

Cloud providers own infrastructure state.

CI systems own their native runs.

Filesystems own files that actually exist.

External engineering systems continue changing whether Monad initiated those changes or not.

That creates an unavoidable problem:

> **What happens when Monad's understanding of a system and the native system itself no longer agree?**

The answer is reconciliation.

```text
Monad model
    │
    │ compare
    ▼
Observed native state
    │
    ▼
Difference
    │
    ├── expected
    ├── stale
    ├── incomplete
    ├── conflicting
    ├── unauthorized
    ├── externally changed
    └── unknown
         │
         ▼
Reconciliation decision
         │
         ├── update Monad
         ├── update native system
         ├── preserve both
         ├── escalate
         ├── defer
         └── require human resolution
```

Reconciliation is not merely synchronization.

Synchronization attempts to make states match.

Reconciliation first asks whether they **should** match, which side has authority, what actually happened, and what action—if any—is legitimate.

<Callout type="info" title="Agreement is not automatically correctness">
Two systems can agree and still be wrong. Reconciliation establishes correspondence between states; it does not by itself prove that either state satisfies the governing Requirement or Specification.
</Callout>

# Requirement family scope

The `REQ-REC-*` family governs reconciliation across:

* filesystems,
* Git repositories,
* issue trackers,
* pull requests,
* CI systems,
* package registries,
* deployment platforms,
* cloud infrastructure,
* databases,
* configuration systems,
* documentation systems,
* artifact stores,
* identity providers,
* policy systems,
* generated projections,
* external APIs,
* and other native engineering systems.

These requirements govern:

* observation,
* comparison,
* divergence classification,
* authority,
* conflict handling,
* convergence,
* partial failure,
* provenance,
* freshness,
* retry,
* repair,
* and historical preservation.

They do not require all integrated systems to use the same storage model or synchronization protocol.

# Foundational reconciliation requirements

## REQ-REC-001 — Monad MUST distinguish reconciliation from synchronization

Synchronization asks:

> How do we make these states match?

Reconciliation asks:

> What are the states, why do they differ, which state is authoritative for which Claims, and what should happen next?

Synchronization MAY be one outcome of reconciliation.

---

## REQ-REC-002 — Monad MUST distinguish reconciliation from verification

Reconciliation establishes agreement or explains disagreement.

Verification evaluates an explicit expectation.

Example:

```text
Monad state: branch exists
Git state: branch exists
reconciliation: agreement
```

does not establish:

```text
branch satisfies release policy
```

---

## REQ-REC-003 — Monad MUST distinguish reconciliation from observation

Observation obtains state.

Reconciliation reasons about relationships between observed states.

---

## REQ-REC-004 — Monad MUST distinguish reconciliation from authority

A state may exist without being authoritative.

A state may be authoritative for one property and non-authoritative for another.

---

## REQ-REC-005 — Monad MUST distinguish divergence from error

Difference does not automatically mean something is wrong.

Divergence may represent:

* expected latency,
* deliberate local work,
* an externally authored change,
* a valid independent representation,
* a pending transaction,
* stale observation,
* partial propagation,
* conflicting authority,
* or actual inconsistency.

---

## REQ-REC-006 — Reconciliation MUST preserve uncertainty when cause or authority cannot be determined

Unknown MUST remain distinguishable from conflict, failure, and absence.

---

# Native systems remain first-class

## REQ-REC-007 — Monad MUST treat native engineering systems as first-class sources of observed reality

Monad SHOULD NOT assume that every relevant engineering change originates through Monad.

---

## REQ-REC-008 — Direct native-system changes MUST be expected unless explicitly prohibited by governance

For example:

```text
developer edits source directly
developer creates Git branch
maintainer closes GitHub issue
registry administrator yanks package
operator changes deployment
```

Monad must be able to discover and reason about such changes.

---

## REQ-REC-009 — Monad MUST NOT require replacement of well-functioning native systems solely to simplify reconciliation

The preferred pattern is:

> integrate before reimplementing.

---

## REQ-REC-010 — Native references SHOULD preserve native identity

Examples include:

* Git commit SHA,
* Git ref,
* GitHub issue ID,
* pull request number,
* deployment ID,
* package digest,
* registry version,
* CI run ID,
* filesystem path.

---

## REQ-REC-011 — Native identity MUST remain distinct from semantic identity

A file path may change while the represented Subject remains the same.

A GitHub issue number may identify a native issue representation without becoming the universal semantic identity of the underlying engineering concern.

---

# Authority-aware reconciliation

## REQ-REC-038 — Reconciliation MUST consult authority before deciding which state should prevail

---

## REQ-REC-039 — Authority SHOULD be scoped to the relevant property or Claim

---

## REQ-REC-040 — Native-system ownership of a capability SHOULD normally imply native authority over native facts produced by that capability unless explicitly overridden

For example:

* Git owns whether commit `81d91ef` exists.
* GitHub owns whether native issue `#42` is open.
* an OCI registry owns whether digest `sha256:...` is published there.
* a deployment system owns whether deployment `D-104` exists.

Monad may interpret those facts.

It should not fabricate them.

---

## REQ-REC-041 — Monad MAY remain authoritative for semantic state that native systems do not own

Examples include:

* semantic identity,
* cross-system relationships,
* authority assignments,
* evidence relationships,
* engineering classification,
* lifecycle interpretation,
* governance state.

---

## REQ-REC-042 — Reconciliation MUST support mixed authority

A single Subject MAY contain properties owned by different authorities.

---

## REQ-REC-043 — Authority ambiguity SHOULD cause explicit conflict or escalation rather than arbitrary overwrite

---

## REQ-REC-044 — Newer state MUST NOT automatically win

Time does not determine authority.

---

## REQ-REC-045 — More persistent state MUST NOT automatically win

A record existing longer does not make it authoritative.

---

## REQ-REC-046 — Native permission MUST NOT be confused with semantic authority

An API allowing an actor to modify a resource does not mean Monad governance authorizes the modification.

# Reconciliation anti-patterns

## Last write wins

Time alone does not establish authority.

---

## Monad always wins

Monad does not own every native fact.

---

## Native always wins

Native systems do not necessarily own semantic Claims.

---

## Difference means failure

Some divergence is expected.

---

## Synchronize first, understand later

This risks destroying valid state.

---

## Missing means deleted

Observation may have failed.

---

## Permission denied means absent

It does not.

---

## API call returned 200

Execution success is not convergence.

---

## Retry everything

Repeated non-idempotent actions may create further corruption.

---

## Rewrite history after conflict resolution

Resolution should preserve how the conflict occurred.

---

## Generated output is canonical

Derived state should not silently become authoritative.

---

## Newer state is better

A newer unauthorized state may be less authoritative than an older governed one.

---

## Semantic identity equals path

Renames then become false deletion and recreation.

---

## Bidirectional sync by default

This creates unnecessary authority ambiguity and feedback loops.

---

## Events are truth

Events can be lost, reordered, delayed, or duplicated.

---

## Zero drift means healthy

Observation may simply be broken.

---

## Agreement means correct

Two wrong systems can agree.

---

## AI similarity means same Subject

Similarity is evidence for a candidate binding, not automatic identity.

# Relationship to native engineering systems

The reconciliation model depends on a simple principle:

> Native systems remain real.

Monad should not create a parallel fantasy in which the semantic graph is treated as reality merely because it is internally coherent.

Instead:

```text
Native systems
      ↕
Observation / Execution
      ↕
Reconciliation
      ↕
Semantic system model
```

The semantic model provides cross-system meaning.

Native systems continue providing native facts.

Reconciliation keeps those worlds connected.

---

# Relationship to semantic identity

Native systems primarily identify their own resources.

Monad identifies engineering Subjects across those systems.

That allows:

```text
Subject
  ├── represented-by → filesystem document
  ├── tracked-by     → GitHub issue
  ├── implemented-by → Git commit
  ├── released-as   → package
  └── evidenced-by  → CI result
```

If one native reference changes, the Subject does not necessarily change.

This is why reconciliation depends on identity being independent of location.

---

# Relationship to authority

Reconciliation without authority becomes arbitrary synchronization.

The critical question is not:

> Which side changed most recently?

It is:

> Which source is authoritative for this particular Claim under this scope?

Therefore:

```text
Authority
    ↓ constrains
Reconciliation
    ↓ may authorize
Mutation
```

Authority should be explicit enough that the system can explain why one state was accepted over another.

---

# Relationship to verification

Reconciliation answers:

> Do these states correspond as expected?

Verification answers:

> Does the system satisfy the Requirement?

A healthy control loop may therefore look like:

```text
Observe
   ↓
Reconcile
   ↓
Execute correction
   ↓
Observe again
   ↓
Verify convergence
   ↓
Verify broader requirement
```

---

# Relationship to provenance

When divergence appears, the first engineering question is often:

> What changed this?

Useful reconciliation therefore depends heavily on provenance:

```text
producer
source
native event
requested operation
resolved target
execution location
observed state
recorded Claim
```

Without provenance, reconciliation can detect mismatch but struggle to explain it.

---

# Relationship to Evidence

For example:

```text

  deployment provider response
  observed artifact digest
  observation timestamp
```

The conclusion becomes explainable rather than asserted.

# Relationship to execution

Reconciliation may lead to execution.

But it should not bypass execution governance.

The sequence should conceptually remain:

```text
Observe
  ↓
Detect divergence
  ↓
Classify
  ↓
Determine authority
  ↓
Plan
  ↓
Govern
  ↓
Revalidate
  ↓
Execute
  ↓
Observe
  ↓
Verify
  ↓
Record Evidence
```

# Relationship to releases

Release state spans multiple native systems:

* source control,
* CI,
* artifact stores,
* package registries,
* deployment systems,
* release portals.

A release may therefore be internally recorded as complete while publication or deployment is only partially reflected in native systems.

Reconciliation is what prevents the release record from drifting away from observable reality.

---

# Relationship to AI

AI makes reconciliation potentially more powerful and more dangerous.

AI can infer:

* likely Subject matches,
* likely causal relationships,
* likely conflict classes,
* likely remediation.

But those are not automatically authoritative conclusions.

A safe pattern is:

```text
Observed divergence
      ↓
AI interpretation
      ↓
Candidate classification
      ↓
Policy / human / deterministic confirmation
      ↓
Authorized action
```

The richer the inference, the more important it becomes to preserve the distinction between:

```text
observed
inferred
confirmed
authorized
executed
verified
```

# Reconciliation as a control loop

The broader system loop becomes:

```text
System intent
      ↓
Semantic model
      ↓
Governed execution
      ↓
Native systems
      ↓
Observation
      ↓
Reconciliation
      ↓
Verification
      ↓
Evidence
      ↓
Updated understanding
      ↓
Semantic model
```

This loop allows Monad to remain connected to reality without demanding that all reality be mediated through Monad.

# Definition of Ready

A reconciliation activity is ready when:

* the target Subject is identifiable,
* the native system is identifiable,
* the native reference is known where applicable,
* relevant modeled state exists,
* native state can be observed,
* comparison semantics are sufficiently defined,
* authority is known or ambiguity is explicitly recognized,
* intended actions are known where mutation may occur,
* required capabilities are available,
* required policies can be evaluated,
* relevant revisions can be identified,
* side effects are understood,
* verification strategy is available,
* and partial-failure handling is defined where necessary.

---

# Definition of Done

A consequential reconciliation is complete enough when:

* relevant native state was actually observed,
* observation provenance is retained,
* modeled and native states were compared,
* divergence or agreement is explicit,
* authority was considered,
* unresolved ambiguity remains visible,
* any proposed action was governed,
* current revisions were revalidated where needed,
* execution outcomes are explicit,
* partial failures are explicit,
* native state was re-observed after mutation where appropriate,
* convergence was verified,
* unresolved divergence remains visible,
* relevant Evidence is linked,
* and reconciliation history is preserved.

# Governing principle

Monad should always be able to ask:

> What does Monad currently believe?

> What does the native system actually report?

> When was that native state observed?

> Is the observation fresh?

> Which exact native revision was observed?

> What differs?

> Is the difference meaningful?

> Is the difference expected?

> Which side is authoritative for this particular property?

> Is authority itself conflicted?

> Did the change originate through Monad or externally?

> Was the external change legitimate?

> Is the difference merely propagation delay?

> Is any state unknown because observation failed?

> Could a rename be mistaken for deletion?

> Could two resources represent the same Subject?

> Could one Subject have split into several?

> Is remediation allowed?

> Does the actor have capability?

> Does the actor have authority?

> Is approval required?

> Has state changed since the reconciliation plan was made?

> What happened when remediation executed?

> Did every native system converge?

> Did only some systems converge?

> Was the result verified afterward?

> Does agreement prove only consistency, or actual correctness?

> What history should remain after convergence?

> What Evidence would show that the reconciliation conclusion was wrong?

Reconciliation should therefore be understood as:

```text
observation
+
semantic identity
+
comparison
+
authority
+
provenance
+
governed remediation
+
verification
```

not as blind synchronization.

> **Monad should reconcile its model with reality without confusing its model for reality, native state for universal authority, or convergence for correctness.**
