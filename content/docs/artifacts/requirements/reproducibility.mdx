# Reproducibility Requirements

Software engineering repeatedly asks questions whose answers depend on conditions that may no longer exist:

* Why did this build succeed?
* Why did the same build fail today?
* Which compiler produced this artifact?
* Which configuration was active?
* Which dependency graph was resolved?
* Which source revision was used?
* Which environment variables influenced the result?
* Which AI model produced this output?
* Can this benchmark be repeated?
* Can this migration be reconstructed?
* Can another engineer independently obtain the same result?
* Can a release artifact be rebuilt?
* Can an old verification result still be explained?
* Can a failed operation be reproduced closely enough to diagnose it?

Without sufficient context, engineering history degrades into anecdote.

Monad should preserve enough information around consequential engineering activity that important results can be reconstructed, explained, compared, or deliberately declared non-reproducible.

The governing question is:

> **What must be preserved so that a future engineer can understand and, where required, recreate the conditions that produced an engineering result?**

---

# Reproducibility is not determinism

These concepts overlap but are not identical.

```text
determinism
    =
same inputs
→ same output
```

Reproducibility asks a broader question:

```text
can the relevant conditions
be reconstructed sufficiently
to evaluate the result again?
```

A nondeterministic system can still support meaningful reproducibility.

For example, an AI generation may not reproduce byte-for-byte output, but its:

* provider,
* model,
* prompt,
* context,
* parameters,
* tools,
* source revision,
* and execution time

can still be preserved sufficiently to explain and investigate the generation.

---

# Reproducibility is not portability

Portability asks:

> Can this state move?

Reproducibility asks:

> Can this result be recreated or independently evaluated?

A project may be perfectly portable while its builds are irreproducible.

A build may be reproducible while its underlying project state is difficult to migrate.

Monad should support both without conflating them.

---

# Reproducibility is scoped

No engineering result is simply:

```text
reproducible = true
```

without qualification.

Reproducibility depends on:

* the Subject,
* revision,
* operation,
* environment,
* dependency set,
* configuration,
* tooling,
* external systems,
* time,
* platform,
* architecture,
* network state,
* randomness,
* mutable inputs,
* and required equivalence level.

A better statement is:

```text
Result R
was reproduced
for Revision X
using Method M
under Environment E
within Equivalence Contract C.
```

---

# Equivalence matters

Reproducing something does not always require identical bytes.

Different engineering operations need different equivalence criteria.

Examples:

```text
build artifact
→ byte-for-byte equality

API behavior
→ contract-equivalent responses

benchmark
→ statistically comparable distribution

migration
→ equivalent resulting data state

AI generation
→ equivalent task outcome or bounded evaluation score

documentation build
→ semantically equivalent rendered content

dependency resolution
→ identical lock graph
```

---

## REQ-REPRO-001 — Every reproducibility Claim MUST identify the equivalence being asserted

Examples include:

* byte-identical,
* semantically equivalent,
* behaviorally equivalent,
* structurally equivalent,
* statistically equivalent,
* functionally equivalent,
* or otherwise explicitly defined.

---

# Core reproducibility model

A reproducible engineering result can be reasoned about as:

```text
Inputs
  +
Source Revision
  +
Configuration
  +
Environment
  +
Dependencies
  +
Tools
  +
Policies
  +
External State
  +
Randomness / Seeds
  +
Execution Method
        ↓
Operation
        ↓
Observed Result
        ↓
Evidence
```

Monad does not need to capture every possible environmental fact.

It should capture the facts required to explain or recreate results that matter.

# Reproducibility levels

Monad SHOULD support reasoning about progressively stronger forms of reproducibility.

## Level 0 — Unrecorded

The result exists, but its production context is unknown.

```text
artifact.zip
```

No reliable reconstruction is possible.

---

## Level 1 — Source known

The source revision is known.

```text
commit:
  abc123
```

---

## Level 2 — Toolchain known

Relevant tool versions are recorded.

```text
runtime
compiler
package manager
build tool
```

---

## Level 3 — Dependency state known

Resolved dependency versions are preserved.

---

## Level 4 — Configuration known

Relevant configuration and feature flags are preserved.

---

## Level 5 — Environment known

Operating-system, architecture, environment, and external dependencies are sufficiently described.

---

## Level 6 — Procedure known

The exact invocation or execution method is recorded.

---

## Level 7 — Independent repetition demonstrated

Another execution reconstructs the conditions and produces an equivalent result.

---

## Level 8 — Hermetic or strongly controlled reproduction

External variability is intentionally minimized or eliminated.

## REQ-REPRO-026 — Secrets MUST NOT be captured in reproducibility records merely because they affected execution

# AI reproducibility

AI introduces a special class of reproducibility problems.

The output may depend on:

* provider,
* model family,
* model snapshot,
* system instructions,
* user prompt,
* hidden platform behavior,
* context,
* retrieval results,
* tools,
* tool results,
* temperature,
* sampling configuration,
* random state,
* provider updates,
* safety systems,
* time,
* and external information.

Exact reproduction may be impossible.

That does not justify abandoning provenance.

# Reproducibility records

A conceptual reproducibility record might contain:

```yaml
reproduction:
  id: REPRO-0042

  subject:
    id: BUILD-0017

  source_revision:
    commit: abc123

  operation:
    command: bun run build

  environment:
    os: linux
    architecture: x86_64

  tools:
    bun: 1.x
    node: 24.x

  dependencies:
    lock_digest: sha256:...

  configuration:
    profile: release

  result:
    artifact_digest: sha256:...

  equivalence:
    type: byte-identical

  evidence:
    - EVD-0182
```

The exact schema belongs in a later Specification.

# Reproducibility anti-patterns

## “Works on my machine”

The machine contains undeclared dependencies.

---

## Branch-name provenance

```text
built from main
```

without the immutable revision.

---

## Package manifest without lock state

Declared ranges are mistaken for resolved dependencies.

---

## Container means reproducible

Mutable images and external dependencies remain uncontrolled.

---

## Toolchain assumed

The compiler or runtime version is nowhere recorded.

---

## CI is the environment specification

The build can only be reconstructed by reading an evolving CI implementation.

---

## Logs are enough

Logs describe some events but omit critical inputs.

---

## Cache equals reproduction

A prior artifact is returned from cache and treated as an independent rebuild.

---

## Re-run overwrites history

The previous result disappears.

---

## Exact AI reproduction promised

A probabilistic external model is treated as deterministic.

---

## Prompt only

An AI prompt is preserved but retrieval context, tools, model, and provider state are lost.

---

## Secrets captured wholesale

Reproducibility becomes a credential leak.

---

## Production snapshot everywhere

Sensitive real-world state is copied merely for convenience.

---

## Byte identity everywhere

Expensive deterministic guarantees are imposed where behavioral equivalence would be sufficient.

---

## Behavioral equivalence everywhere

Weak equivalence hides artifact-level nondeterminism where exact builds matter.

---

## Current tools reinterpret history

A new analyzer is run and its results are substituted for the historical analyzer result.

---

## Reproduction success means correctness

The same defect is recreated perfectly.

---

## Reproducible means verified

A repeatable system can still violate its Specification.

---

# Reproduction example: build

Original:

```text
Source: abc123
Bun: 1.2.3
Lockfile: sha256:111...
OS: Linux
Command: bun run build
Artifact: sha256:999...
```

Independent reproduction:

```text
Source: abc123
Bun: 1.2.3
Lockfile: sha256:111...
OS: Linux
Command: bun run build
Artifact: sha256:999...
```

If the contract requires byte equality:

```text
sha256:999... == sha256:999...
```

supports the Claim that the artifact was reproduced.

It does not prove that the artifact is correct.

# Reproduction example: AI generation

Original:

```text
Provider: Provider A
Model: Model X
Prompt: P
Context: C
Tools: T
Output: O1
```

Repeated:

```text
Provider: Provider A
Model: Model X
Prompt: P
Context: C
Tools: T
Output: O2
```

If:

```text
O1 != O2
```

textually, both outputs may still satisfy:

```text
same structured contract
+
same acceptance tests
+
same engineering intent
```

That is a weaker but potentially useful reproducibility contract.

# Reproduction example: migration

Original migration:

```text
Input snapshot: S1
Migration: M42
Tool version: V1
Output state digest: D1
```

Safe reproduction:

```text
restore S1
run M42 with V1
compare resulting state against D1
```

The reproduction should not target the historical production system.

# Reproduction example: static analysis

Historical scan:

```text
Revision: abc123
Analyzer: 3.4
Ruleset: 2026-01
Findings: 7
```

Current scan:

```text
Revision: abc123
Analyzer: 4.0
Ruleset: 2026-08
Findings: 12
```

These are not contradictory reproductions of the same operation.

The analysis environment changed.

Both results can be valid within their respective contexts.

# Reproducibility diagnostics example

Suppose reproduction fails.

Monad should ideally make visible something like:

```text
Original                    Reproduction

source abc123        ==      abc123
runtime 1.2.3        ==      1.2.3
lock digest A        !=      lock digest B
OS linux             ==      linux
config release       ==      release
artifact digest X    !=      artifact digest Y
```

The first useful conclusion is not:

```text
reproducibility broken
```

but:

```text
dependency state differs
```

# Reproducibility quality

A high-quality reproducibility record is:

* scoped,
* revision-aware,
* environment-aware,
* dependency-aware,
* configuration-aware,
* tool-aware,
* explicit about equivalence,
* evidence-backed,
* security-conscious,
* historically preserved,
* and honest about uncertainty.

# Risk-proportional reproducibility

Not every operation deserves a hermetic reconstruction system.

A useful progression is:

```text
low consequence
→ source + basic tool provenance

moderate consequence
→ locked dependencies + environment + configuration

high consequence
→ controlled environment + independent rerun

critical consequence
→ strongly controlled or independently reproducible process
```

# Reproducibility economy

Capturing everything is not automatically better.

The objective is:

> preserve enough context to answer consequential future questions without turning every execution into an exhaustive forensic snapshot.

Prefer recording information that materially affects:

* equivalence,
* diagnosis,
* verification,
* release confidence,
* auditability,
* or future engineering decisions.

# Definition of Ready

A reproducibility capability is ready for implementation when:

* the target operation is identified,
* the required equivalence is defined,
* source revision semantics are known,
* relevant inputs are known,
* toolchain requirements are known,
* dependency-resolution requirements are known,
* environment requirements are known,
* configuration precedence is known,
* secret-handling rules are known,
* external-state dependencies are understood,
* randomness requirements are understood,
* required provenance is defined,
* Evidence requirements are defined,
* reproduction outcome semantics are defined,
* and verification criteria exist.

---

# Definition of Done

A reproducibility capability is complete enough when:

* consequential runs have stable identities,
* source revision is preserved,
* relevant working-tree state is represented,
* input identity is preserved,
* dependency state is preserved,
* relevant tool versions are preserved,
* effective configuration is reconstructable,
* relevant environment facts are preserved,
* secret values are not leaked,
* execution method is known,
* output identity is preserved,
* equivalence criteria are explicit,
* reproduction attempts create separate historical records,
* result comparisons produce Evidence,
* conflicting reproductions remain inspectable,
* stale Evidence can be identified,
* clean reproduction is possible where required,
* unsupported reproduction limitations are explicit,
* and the resulting Claims are no stronger than the Evidence permits.

# Governing principle

Monad should always be able to ask:

> Which exact source state produced this result?

> Was the working tree different from the recorded revision?

> Which dependencies were actually resolved?

> Which runtime and tool versions were used?

> Which configuration was effective?

> Which environment assumptions mattered?

> Did a cache supply the output?

> Was the operation actually rerun?

> Did external mutable state influence it?

> Does randomness prevent exact reproduction?

> What does “same result” mean for this operation?

> Do we require identical bytes or equivalent behavior?

> Which Evidence demonstrates equivalence?

> Was the result independently reproduced?

> Does the current environment still match the original one?

> Does historical reproduction Evidence still apply?

> Can this Release be rebuilt?

> Can this migration be reconstructed safely?

> Can this benchmark be compared meaningfully?

> Can this AI output be explained even if it cannot be regenerated exactly?

> If reproduction fails, can we identify what changed?

> If reproduction succeeds, have we accidentally confused repeatability with correctness?

The desired system is not:

```text
capture every possible environmental fact
```

and it is not:

```text
pretend every engineering operation can be made perfectly deterministic
```

It is:

```text
known source
     +
known inputs
     +
known dependencies
     +
known tools
     +
known configuration
     +
known environment
     +
known execution method
     +
known output
     +
explicit equivalence
     +
inspectable Evidence
        ↓
explainable and repeatable engineering results
```

> **Monad should preserve enough execution context that consequential engineering results can be explained, reconstructed, compared, and independently challenged without relying on the memory of the machine or engineer that originally produced them.**
