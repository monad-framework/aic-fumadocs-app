# Verification Requirements

Engineering systems routinely claim that something is correct.

A Requirement is satisfied.

An interface conforms to its Specification.

A migration preserved the required state.

A policy behaved correctly.

A release is ready.

A generated artifact matches its source.

An implementation preserves an invariant.

A deployment succeeded.

An AI-produced change is acceptable.

But correctness cannot be established merely by:

* implementation existing,
* execution succeeding,
* a build being green,
* a reviewer approving,
* an agent expressing confidence,
* or a dashboard showing a favorable status.

Monad should make the verification relationship explicit:

```text id="3l2jyq"
Expectation
    ↓
Verification Method
    ↓
Execution / Inspection
    ↓
Observation
    ↓
Evidence
    ↓
Verification Result
```

Verification exists to answer:

> **Did the observed system satisfy the explicit expectation within the scope actually examined?**

<Callout type="info" title="Verification is scoped">
A passed verification result establishes satisfaction only for the expectation, revision, environment, inputs, assumptions, and conditions actually evaluated. It does not establish universal correctness.
</Callout>

# Requirement family scope

The `REQ-VFY-*` family governs verification of:

* Requirements,
* Specifications,
* invariants,
* implementations,
* interfaces,
* schemas,
* policies,
* migrations,
* integrations,
* reconciliation,
* releases,
* generated artifacts,
* projections,
* runtime behavior,
* security properties,
* compatibility commitments,
* performance commitments,
* AI-generated outputs,
* and other explicit engineering Claims.

These requirements govern the semantics and lifecycle of verification.

They do not prescribe one testing framework, CI provider, programming language, or execution environment.

# Foundational verification requirements

## REQ-VFY-001 — Monad MUST distinguish verification from implementation

Implementation answers:

> What was built?

Verification answers:

> Does what was built satisfy the explicit expectation?

The existence of implementation MUST NOT automatically imply verification.

---

## REQ-VFY-002 — Monad MUST distinguish verification from execution

Successful execution establishes that an operation completed according to some execution semantics.

It does not necessarily establish that the resulting state is correct.

For example:

```text id="pq7u38"
Execution:
  database migration exited with status 0

Verification:
  all expected records remain present
  schema matches required structure
  application reads migrated records correctly
```

These are different Claims.

---

## REQ-VFY-003 — Monad MUST distinguish verification from Evidence

Verification evaluates an expectation.

Evidence is the inspectable information used to support that evaluation.

---

## REQ-VFY-004 — Monad MUST distinguish verification from approval

A state may be:

```text id="akd3vf"
verified but not approved
```

or:

```text id="pze8dg"
approved despite incomplete verification under an explicit exception
```

Those states MUST remain distinguishable.

---

## REQ-VFY-005 — Monad MUST distinguish verification from review

Review is structured examination.

Verification evaluates an explicit expectation against defined criteria.

A review MAY function as a verification method when that relationship is explicit.

---

## REQ-VFY-006 — Monad MUST distinguish verification from confidence

A human or AI actor may be highly confident that something is correct.

Confidence is not itself a verification result.

---

## REQ-VFY-007 — Verification MUST evaluate an identifiable expectation

A verification activity SHOULD answer something more precise than:

```text id="77sfsc"
Does this look okay?
```

The expectation MAY originate from:

* Requirement,
* Specification,
* invariant,
* policy,
* interface contract,
* migration plan,
* release criterion,
* acceptance criterion,
* architecture constraint,
* or another explicit Claim.

# Verification identity

## REQ-VFY-008 — Consequential verification activities SHOULD have stable identity

Verification that participates in:

* Requirement satisfaction,
* release readiness,
* governance,
* auditability,
* migration acceptance,
* architecture conformance,
* or historical assurance

SHOULD be independently identifiable.

---

## REQ-VFY-009 — Verification identity SHOULD remain distinct from verification runs

One verification definition may execute multiple times.

Conceptually:

```text id="yefqff"
Verification Method
  ├── Run 1
  ├── Run 2
  ├── Run 3
  └── Run 4
```

The method and individual executions SHOULD remain distinguishable.

---

## REQ-VFY-010 — Verification identity MUST NOT depend solely on file location

Moving a verification definition SHOULD NOT automatically create a new semantic Verification if its engineering identity remains unchanged.

# Verification expectations

## REQ-VFY-012 — Verification expectations SHOULD be explicit before consequential evaluation

Where practical, the expected condition SHOULD be known before observing the result.

This reduces post hoc reinterpretation.

---

## REQ-VFY-013 — Verification expectations SHOULD be implementation-independent where the underlying Requirement is implementation-independent

For example:

```text id="13xksh"
Requirement:
  semantic identity survives representation rename
```

should not become:

```text id="64o6bc"
Verification:
  internal function renameSubject() returns true
```

unless that internal function is itself the contractual behavior.

---

## REQ-VFY-014 — Verification expectations SHOULD identify success criteria

A method SHOULD make it possible to determine what constitutes:

* pass,
* fail,
* incomplete,
* blocked,
* inconclusive,
* or another defined outcome.

---

## REQ-VFY-015 — Verification expectations SHOULD identify material failure conditions

---

## REQ-VFY-016 — Verification expectations SHOULD expose assumptions that materially affect interpretation

# Requirement verifiability

## REQ-VFY-017 — Accepted Requirements SHOULD be verifiable where the Requirement represents observable behavior or state

A Requirement that cannot plausibly be verified SHOULD be challenged for ambiguity or incorrect abstraction.

---

## REQ-VFY-018 — Verification strategy SHOULD be considered during Requirement definition

Verification SHOULD NOT be deferred until after implementation if doing so would expose that the Requirement is not measurable or testable.

---

## REQ-VFY-019 — Requirements MAY define acceptance criteria separately from the verification mechanism

For example:

```text id="l5r43j"
Requirement:
  identity survives representation rename

Acceptance criterion:
  rename does not produce a new Subject identity

Verification method:
  integration test
```



# Verification anti-patterns

## Build passed

A build proves only what the build process actually evaluates.

---

## Tests passed

Tests establish only the properties those tests meaningfully exercise.

---

## Reviewer approved

Approval is governance.

It is not automatically verification.

---

## CI is green

Green CI may aggregate:

* incomplete coverage,
* skipped tests,
* stale results,
* irrelevant checks.

---

## Zero failures means correct

A verification method may simply be incapable of detecting the defect.

---

## Rerun until green

This destroys information about flakiness.

---

## All code paths executed

Coverage is not semantic correctness.

---

## No issue reported

Absence of observed failure is not proof of correctness.

---

## Latest result wins

The latest result may:

* apply to a different revision,
* use a weaker method,
* cover narrower scope,
* be invalid.

---

## One verifier says pass

Verifier identity alone does not establish correctness.

---

## AI says it looks good

Probabilistic judgment is not automatically deterministic verification.

---

## Migration returned zero

Execution success does not establish state correctness.

---

## Both systems agree

Reconciliation agreement does not establish that either system is correct.

---

## Generated output exists

Generation success does not establish projection correctness.

---

## Security scanner found nothing

This verifies only what that scanner could detect under its configuration.

---

## Manual review completed

Completion of review does not guarantee an explicit expectation was verified.

---

## Waived

A waiver means the obligation was bypassed under authority.

It does not mean the obligation was satisfied.

---

# Relationship to Evidence

Verification asks:

> **Does the system satisfy the expectation?**

Evidence answers:

> **What observations support the verification result?**

The two form a chain:

```text id="8o53fb"
Expectation
    ↓
Verification
    ↓
Evidence
    ↓
Result
```

A result without Evidence may be difficult to trust.

Evidence without an expectation may be difficult to interpret.

---

# Relationship to Requirements

Requirements define what must be true.

Verification determines whether those required conditions have been demonstrated.

A Requirement should not merely have:

```text id="rxuuwx"
implementation: complete
```

It should be capable of reaching:

```text id="9g0ohp"
verification: pass
```

within a known scope.

---

# Relationship to Specifications

Specifications define precise normative behavior.

Verification evaluates whether implementation conforms to that behavior.

The Specification is the contract.

Verification is the evaluation.

Evidence is the observable support.

---

# Relationship to review

Review provides structured engineering challenge.

Verification provides explicit evaluation against an expectation.

Sometimes a review itself is an appropriate method.

Sometimes it is not.

The relationship should be explicit rather than assumed.

---

# Relationship to approval

Approval is an exercise of governance Authority.

Verification is an engineering assurance activity.

A release manager may approve a release after examining verification results.

That approval does not cause those verification results to become true.

---

# Relationship to execution

Execution changes or interrogates real systems.

Verification evaluates whether the resulting or observed state satisfies expectations.

The operating loop therefore looks like:

```text id="r4jzti"
Intent
  ↓
Plan
  ↓
Governance
  ↓
Execution
  ↓
Observation
  ↓
Verification
  ↓
Evidence
  ↓
Reconciliation
  ↓
Lifecycle Update
```

Execution is not the end of the reasoning chain.

It creates new reality that must often be verified.

---

# Relationship to reconciliation

Reconciliation answers:

> Do the relevant states agree?

Verification asks:

> Does the relevant state satisfy the required condition?

These may overlap.

They are not equivalent.

---

# Relationship to releases

A release is a consequential assertion about a specific artifact or revision.

Release readiness therefore should depend on explicit verification obligations rather than generalized confidence.

A release should be able to answer:

* Which Requirements mattered?
* Which verifications applied?
* Which passed?
* Which failed?
* Which were incomplete?
* Which were waived?
* What Evidence supported them?
* Which exact artifact was evaluated?

---

# Relationship to AI systems

AI increases the importance of verification rather than reducing it.

An AI system can produce implementation faster than humans can manually inspect every detail.

That changes the economics of assurance.

It does not change the fundamental requirement:

> Generated work must still satisfy explicit engineering expectations.

AI can help generate:

* tests,
* invariants,
* fixtures,
* verification plans,
* review findings,
* impact analysis,
* candidate Evidence interpretations.

But AI should not be able to collapse:

```text id="iqk9j2"
I generated it.
```

into:

```text id="m6s983"
Therefore it is correct.
```

The same principle applies to humans.

---

```text id="xdrsjv"

  ↓
```

* implementation from masquerading as correctness,
* automation from masquerading as assurance,
* approval from masquerading as Evidence,
* and confidence from masquerading as demonstrated truth.

---

# Definition of Ready

A verification activity is ready when:

* the target Subject is identifiable,
* the expectation is explicit,
* the relevant Requirement or Specification is known,
* the relevant revision is known where required,
* scope is sufficiently defined,
* success criteria are sufficiently defined,
* failure criteria are sufficiently defined,
* the verification method is appropriate,
* required inputs and fixtures are available,
* required environment is available,
* Evidence capture is possible,
* known exclusions are explicit,
* required authority for side-effecting verification is available,
* and any dependencies or assumptions are understood.

---

# Definition of Done

A consequential verification activity is complete enough when:

* the target expectation was evaluated,
* the applicable revision is recorded,
* the scope is recorded,
* the method is identifiable,
* relevant tool and environment provenance is preserved,
* the result is explicit,
* uncertainty is preserved,
* incomplete or blocked states are not hidden,
* relevant Evidence is linked,
* contradictory Evidence is retained,
* exclusions are visible,
* retries or flakiness are represented,
* any invalidation condition is known,
* any waiver is separate from pass state,
* any required follow-up is visible,
* and downstream assurance state can be traced back to the verification.

---

# Core invariants

The verification system SHOULD preserve these distinctions:

```text id="6z9oyv"
Verification ≠ Evidence

Verification ≠ Approval

Verification ≠ Review

Verification ≠ Execution

Verification ≠ Confidence

Execution success ≠ Verification success

Implementation complete ≠ Requirement satisfied

Reconciliation success ≠ Correctness

Schema-valid ≠ Semantically correct

Generated ≠ Verified

Passed once ≠ Universally correct

Historical pass ≠ Current pass

Stale pass ≠ Current pass

Incomplete ≠ Pass

Blocked ≠ Fail

Inconclusive ≠ Pass

Waived ≠ Pass

Reviewer authority ≠ Verification correctness

AI opinion ≠ Deterministic verification

Native tool pass ≠ Broader Claim automatically

Coverage ≠ Correctness

More tests ≠ More assurance automatically

No observed failure ≠ Proof of absence

Verification result ≠ Universal truth
```

These distinctions are not pedantic.

They prevent the assurance system from producing false certainty.

---

# Governing principle

Monad should make it possible to ask:

> What exactly was expected?

> Where was that expectation defined?

> What method evaluated it?

> Against which revision?

> Under what conditions?

> What was actually observed?

> What Evidence supports the result?

> What was not evaluated?

> Was any part blocked?

> Was anything waived?

> Was the result probabilistic?

> Did execution succeed independently of verification?

> Has relevant state changed since verification?

> Is the result still fresh?

> Can the method detect the failure it claims to detect?

> Can the result be reproduced?

> Does contradictory Evidence exist?

> Is approval being confused with correctness?

> Is an AI judgment being treated as stronger than it is?

> What change would force reverification?

> What Evidence would falsify this result?

Verification should therefore be understood as a disciplined relationship between:

```text id="92wm46"
explicit expectation
+
defined method
+
observed state
+
inspectable Evidence
+
scoped result
```

not as a green icon.

> **An engineering state should be considered verified only when an explicit expectation has been evaluated against appropriate, inspectable Evidence within a known scope.**
