Software projects usually show you the result.

A repository contains the code that survived. Documentation explains the architecture that exists now. An ADR may preserve an important decision. An issue tracker contains fragments of work. Git retains the changes.

But most of the actual engineering process disappears.

The questions that exposed the problem.

The alternatives that almost won.

The assumptions that turned out to be wrong.

The experiments that changed the architecture.

The half-correct ideas that eventually became good ones.

The reasoning connecting one stage of the system to the next.

**Building Monad exists to preserve that process.**

<Callout type="info" title="This is not the authoritative technical documentation">

Building Monad records the **evolution of the project**.

If you want the current authoritative explanation of Monad, go to [System](/docs/system).

If you want requirements, specifications, ADRs, experiments, reviews, and other inspectable engineering records, go to [Artifacts](/docs/artifacts).

</Callout>

## What is Building Monad?

Building Monad is the public narrative layer of the Monad project.

It follows the project from its earliest questions through research, domain discovery, product definition, architecture, specification, implementation, verification, release, and continued evolution.

It is part engineering journal, part long-form technical series, part project history, and part open research record.

The goal is not merely to say:

> Here is what we built.

The more interesting questions are:

> Why did we build it this way?

> What did we believe before we knew what we know now?

> What evidence changed our minds?

> Which ideas failed?

> Which constraints forced the architecture to evolve?

> What remains unresolved?

> And could someone else reconstruct the reasoning that produced the system?

That is what this section attempts to preserve.

## Why build in public?

There are practical reasons to publish an engineering project while it is being built.

But the deeper reason is architectural.

Monad is concerned with the problem of **engineering knowledge** itself.

Modern software projects produce enormous amounts of information:

- ideas,
- goals,
- constraints,
- requirements,
- domain knowledge,
- specifications,
- architectural decisions,
- source code,
- tests,
- experiments,
- evidence,
- issues,
- discussions,
- reviews,
- commits,
- releases,
- operational observations,
- and the reasoning connecting all of them.

Most software development environments preserve the individual pieces better than they preserve the **meaning between the pieces**.

Building Monad is therefore more than a communication strategy.

It is also an experiment.

By deliberately preserving the development of Monad, the project creates a real corpus against which its own ideas about engineering knowledge can be tested.

In that sense, Monad is one of its own first subjects.

---

## The process is part of the product

A conventional project might treat these as disposable intermediate states:

question
   ↓
discussion
   ↓
hypothesis
   ↓
experiment
   ↓
decision
   ↓
specification
   ↓
implementation

Only the implementation may survive as something developers regularly encounter.

But every transition contains knowledge.

Why did that question matter?

Which hypotheses were considered?

What evidence distinguished them?

Why was one direction selected?

What constraint does the resulting specification encode?

What happens if that constraint changes later?

If those relationships disappear, future engineers are forced to reconstruct them.

Humans do this constantly.

AI systems face exactly the same problem.

Building Monad intentionally preserves more of that chain.

## Three layers of the project

The public Monad knowledge base is deliberately divided into three different kinds of record.

### Building Monad — what happened?

This section preserves the evolving story.

It includes:

* essays,
* installments,
* engineering journal entries,
* project phases,
* discoveries,
* working hypotheses,
* failed approaches,
* turning points,
* retrospectives,
* and major transitions in the project.

It is chronological and interpretive.

It can contain things that later become obsolete because **being wrong at a particular point in the project's history is itself historical information**.

### System — what is true now?

[System](/docs/system) contains the current authoritative explanation of Monad.

It should tell you what the system currently is without requiring you to read its entire history.

When the project's understanding changes, System changes.

The old understanding does not need to remain authoritative merely because it once was.

### Artifacts — why can we claim that?

[Artifacts](/docs/artifacts) contains the inspectable engineering record.

Depending on the stage of the project, that includes things such as:

* requirements,
* specifications,
* ADRs,
* domain models,
* schemas,
* experiments,
* evidence,
* reviews,
* verification results,
* work products,
* and relationship indexes.

Together, the three layers create a useful separation:

Building Monad
     │
     │ records
     ▼
What happened?
     │
     │ produces
     ▼
Decisions + Artifacts + Evidence
     │
     │ support
     ▼
System
     │
     │ describes
     ▼
What is true now?

The history does not masquerade as current truth.

Current truth does not erase history.

And neither has to exist without inspectable evidence.

## Project phases

Monad is being developed as an engineering program rather than a single implementation sprint.

The exact boundaries can evolve, but the narrative broadly follows this progression.

### 01 — Inception

What problem are we actually trying to solve?

Before architecture, before technology selection, and before implementation, establish whether there is a problem worth solving at all.

Topics include:

* problem discovery,
* motivating observations,
* first principles,
* project thesis,
* assumptions,
* falsification conditions,
* boundaries,
* goals,
* non-goals,
* and definitions of success.

### 02 — Domain discovery

What actually exists in the problem domain?

This phase attempts to identify concepts before encoding them in architecture.

Topics include:

* semantic identity,
* subjects,
* representations,
* claims,
* authority,
* provenance,
* evidence,
* lifecycle,
* context,
* relationships,
* and system state.

### 03 — Product definition

What should Monad actually do?

This turns an increasingly understood problem into product and system capabilities.

Topics include:

* actors,
* workflows,
* use cases,
* capabilities,
* requirements,
* constraints,
* product boundaries,
* minimum viable system,
* and success criteria.

### 04 — Architecture

What system could satisfy those requirements?

Topics include:

* system decomposition,
* authority boundaries,
* semantic model,
* storage,
* interfaces,
* execution,
* policy,
* governance,
* AI integration,
* projections,
* and architectural decisions.

### 05 — Specification

Turn architectural intent into contracts precise enough to implement and verify.

Topics include:

* specifications,
* schemas,
* protocols,
* lifecycle state machines,
* CLI behavior,
* provider contracts,
* policies,
* acceptance criteria,
* and verification requirements.

### 06 — Implementation

Build the system incrementally against those contracts.

The narrative here moves much closer to software construction:

* repositories,
* source code,
* build systems,
* tests,
* integrations,
* migrations,
* tooling,
* automation,
* debugging,
* and engineering tradeoffs.

### 07 — Verification

Determine whether what was built actually satisfies what was intended.

This includes:

* acceptance testing,
* architecture conformance,
* reproducibility,
* security,
* performance,
* failure testing,
* operational evaluation,
* and evidence collection.

### 08 — Release and evolution

A system is not finished when the first version ships.

The project eventually becomes a continuous cycle:

observe
   ↓
learn
   ↓
propose
   ↓
decide
   ↓
change
   ↓
verify
   ↓
release
   ↓
observe

That evolution becomes part of Building Monad too.

## Engineering journal

The polished narrative will never contain everything.

Nor should it.

The engineering journal preserves a record closer to the actual work.

A journal entry might begin with something as small as:

> We assumed representations should own identity. Today's domain work suggests that identity belongs to the underlying subject instead.

Or:

> The first implementation exposed a conflict between filesystem authority and semantic authority. We need to resolve the authority model before continuing.

Or:

> This experiment failed. The proposed graph model created more representational complexity than the retrieval problem justified.

Those moments matter.

Later, they may become:

journal observation
        ↓
open question
        ↓
experiment
        ↓
evidence
        ↓
decision
        ↓
ADR
        ↓
specification
        ↓
implementation

The journal preserves the beginning of that chain.

## Installments

Installments are the main published chapters of Building Monad.

Unlike journal entries, they are written retrospectively enough to tell a coherent story.

An installment should generally answer:

1. Where were we?
2. What problem were we working on?
3. What did we believe?
4. What did we discover?
5. What changed?
6. What evidence or reasoning caused the change?
7. What exists now?
8. What remains unresolved?
9. What happens next?

This creates an engineering narrative without pretending the path was obvious in advance.

## The project may be wrong

Building in public is much less useful if every post is written as though every decision was inevitable.

Monad begins with hypotheses.

Some may survive.

Some may require substantial revision.

Some may turn out to be unnecessary complexity.

Some may be wrong.

For example, the project should remain willing to ask:

* Is a semantic system model actually necessary?
* Could simpler indexing and retrieval produce most of the value?
* Are we modeling knowledge that should instead remain implicit?
* Does the cost of maintaining richer semantics exceed its benefit?
* Will developers actually preserve the information the model requires?
* Can useful authority be encoded without creating intolerable friction?
* Are we solving a fundamental problem or merely reorganizing its symptoms?
* Does AI materially change the problem, or only make existing weaknesses more visible?

A serious engineering record should preserve evidence against the project as readily as evidence for it.

<Callout type="idea" title="Failure is a valid project outcome">

If a major Monad hypothesis is disproven, documenting why it failed is still a successful outcome of the investigation.

The purpose is not to prove the original idea correct.

The purpose is to discover what is actually true.

</Callout>

## You are not reading a finished history

Most technical histories are written after success.

That creates an unavoidable distortion.

Dead ends disappear.

Uncertainty gets compressed.

Early assumptions are forgotten.

The final architecture begins to look more inevitable than it actually was.

Building Monad is different because much of it is being written **before the outcome is known**.

You are seeing the project while:

* important questions remain unanswered,
* architectural boundaries are still being tested,
* specifications are evolving,
* implementations expose flaws in earlier thinking,
* and some of the project's core hypotheses remain falsifiable.

That uncertainty is intentional.

It is part of the record.

## Current state

Monad is a living engineering program.

At any point, the project can contain several different levels of maturity simultaneously:

| State           | Meaning                                                           |
| --------------- | ----------------------------------------------------------------- |
| **Question**    | Something important is not yet understood.                        |
| **Hypothesis**  | A possible explanation or direction is being considered.          |
| **Experiment**  | Evidence is being gathered.                                       |
| **Decision**    | A direction has been deliberately selected.                       |
| **Specified**   | The decision has been translated into an implementable contract.  |
| **Implemented** | Working software exists.                                          |
| **Verified**    | Evidence shows the implementation satisfies defined expectations. |
| **Released**    | The capability has entered a supported project state.             |
| **Superseded**  | A newer understanding or implementation has replaced it.          |

Do not assume that every idea you encounter in Building Monad represents the current system.

That is precisely why [System](/docs/system) exists.

## Join the investigation

Monad is being built publicly because software engineering is becoming too consequential—and increasingly too machine-mediated—for its reasoning to remain invisible.

If you are interested in:

* software architecture,
* developer tooling,
* AI-assisted engineering,
* autonomous software agents,
* engineering knowledge,
* semantic systems,
* provenance,
* governance,
* reproducibility,
* software evolution,
* or simply how a complicated engineering idea becomes a real system,

you are invited to follow along.

You do not have to agree with the project's assumptions.

In fact, disagreement backed by evidence is considerably more useful than agreement.

The project gets better when its ideas are forced to survive contact with implementation, criticism, evidence, and reality.
