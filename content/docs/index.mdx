## What Documentation answers

Documentation should help you answer questions such as:

- What is Monad currently understood to be?
- Which concepts and architectural boundaries are authoritative now?
- What requirements constrain a capability?
- Which specification governs an interface or behavior?
- Which ADR records the accepted architectural decision?
- What evidence or verification supports a claim?
- Is a capability merely designed, implemented, released, or actually verified?

It is deliberately optimized for **current interpretation**, not chronological storytelling.

## Three documentation surfaces

| Surface | Primary responsibility | Typical question |
| --- | --- | --- |
| [System](/docs/system) | Current explanatory truth | What is the system now? |
| [Artifacts](/docs/artifacts) | Governed engineering record | What specifies, decides, or supports that claim? |
| [Project](/docs/project) | Current coordination and status context | Where does the work actually stand? |

These surfaces are related but not interchangeable.

A System page may explain a concept without replacing the specification that governs it. An accepted ADR may define an architectural choice without proving that the choice is implemented. A completed implementation may still lack verification evidence.

## How to interpret authority

A useful default progression is:

```text
idea or hypothesis
      ↓
requirement / specification / accepted decision
      ↓
implementation
      ↓
observed result
      ↓
verification evidence
      ↓
current authoritative explanation
```

Real engineering is not always this linear, but the distinctions matter.

**Published does not mean authoritative.**  
**Accepted does not mean implemented.**  
**Implemented does not mean verified.**  
**Historically accurate does not necessarily mean current.**

When two records appear to disagree, prefer the record whose authority and scope actually cover the claim, then use provenance and history to understand why the difference exists.

## Reading paths

### Architect

Start with [System](/docs/system), then follow concepts into the relevant [ADRs](/docs/artifacts/decisions), [requirements](/docs/artifacts/requirements), and [specifications](/docs/artifacts/specifications).

**Route:** current model → decisions → requirements → specifications → evidence.

### Implementer

Start with [Artifacts](/docs/artifacts), identify the governing requirements and specifications, use [System](/docs/system) for current architectural context, and check [Project](/docs/project) before assuming planned capability is available.

**Route:** governing artifacts → implementation context → verification → status.

### Reviewer or auditor

Begin with the claim you need to evaluate, find its governing artifact, inspect related evidence and verification, then compare the result with the current System explanation.

**Route:** claim → authority → provenance/evidence → verification → current interpretation.

## The other public knowledge domains

Documentation is intentionally not the entire public record.

| Domain | Question it answers | Use it when... |
| --- | --- | --- |
| [Engineering Journal](/journal) | What happened while doing the work? | You need chronology, uncertainty, failures, discoveries, or changes in understanding. |
| [Changelogs](/changelogs) | What changed at a meaningful boundary? | You need release/change impact, migration, compatibility, or externally relevant deltas. |
| [Articles](/articles) | What should readers understand about this? | You want editorial explanation, research, or a formal argument. |
| [Building Monad](/building-monad) | How do the records fit together into the story? | You want curated phases, installments, series, and cross-domain reading paths. |

The source record keeps its own responsibility. Building Monad may link an ADR, Journal entry, Changelog, and Article into one narrative sequence, but the curation page does not become authoritative for the technical claims contained in those sources.
